# RuleUpdate: придумай новое правило и раздели данные на старое и новое

Приходят данные ({{INPUT}}), которые не вписываются в текущие правила
({{RULES}}). Часть записей может всё-таки ложиться на старые правила — нужно
это увидеть и не выдумывать для них новый ключ. Контекст последних записей:
{{CONTEXT}}.

## Что сделать

**Сначала проверь, есть ли подходящие существующие правила.** Старым считается только ключ, явно присутствующий в `{{RULES}}`; примеры пользователя, общие знания и каноническое имя ключа не создают существующее правило. Если `{{RULES}}` пуст или в нём нет применимых правил, `oldKeysEvents` обязан быть пустым массивом `[]`; все измеряемые значения этого дня относятся к `newKeys`. Не придумывай старые ключи и не записывай знакомую метрику как старую без правила в `{{RULES}}`.

1. **Раздели данные на две части.**
   - Куски, которые читаются уже существующими ключами из {{RULES}}, —
     это **старые данные**. Для каждого такого куска укажи, каким ключом он
     читается, и переведи его в значения по этому ключу.
   - Куски, для которых в правилах нет подходящего ключа, — это **новые
     данные**. Для них придумай новые ключи (см. нейминг ниже).

   Сохрани каждую измеряемую величину из ввода. Если человек записал общий
   итог и уточнил «из них»/части в скобках, итог — контекстная сумма, а не
   третья величина: внеси значения составляющих по их смыслу и не дублируй
   общий итог отдельным ключом. Для A+B сначала определи смысл каждой части
   по тексту и существующим примерам, затем занеси обе части в один пример.
   Если запись содержит общий итог N и разбивку A+B, где A+B=N, значения
   события — A и B. Фраза «из них M» только называет часть, которая равна M;
   повторно её не добавляй. Скобки и знаки сложения — способ записи значений,
   а не самостоятельная метрика и не основание придумывать ключи `breakdown`.
   Не подменяй части общей суммой. Когда части явно образуют итог, сверь
   арифметику; если текст ей противоречит, не исправляй числа сам — верни
    `ambiguous` и кратко укажи противоречие.

   **Максимум — отдельная метрика, не часть и не замена общего объёма.** Если ввод содержит
   `100 отжимания (макс подход: 32)`, а правило уже знает `push_reps`, включи в
   `oldKeysEvents` `push_reps: 100`; включи в `newKeys` `push_max_set: 32`. Аналогично для pull.
   Не пропускай базовый объём из строки с максимумом.

   **Полнота простых упражнений:** каждую отдельную измеряемую строку без разбиения также включи
   в `rule.keys` и `newKeys`, если подходящего пользовательского правила нет. Например,
   `50 пресс` при пустом словаре обязательно даёт `press_reps: 50`; не пропускай строку, даже если
   тот же день содержит сложные упражнения с парами.

   Эталон для формулировок «N всего, из них B с колен (A+B)»:
   «50 отжимания (+из них около 30 с колен(20+30))» означает ровно
   `push_reps: 20` (обычные) и `push_knees_reps: 30` (с колен). Не создавай
   `push_reps: 50`: 50 — только контекстный итог. Аналогично «25 подтягивания
   (+из них около 20 на кольцах (5+20))» означает `pull_reps: 5` и
   `pull_rings_reps: 20`, без отдельного значения 25. В `relations` укажи
   `base: push_reps`, `parts: [push_knees_reps]` (и аналогично для pull):
   base — первая составляющая A, parts — оставшиеся составляющие B.

2. **Придумай новое правило** для новых данных: подбери ключи, роли и для
   КАЖДОГО ключа укажи его **смысл** (mapping) — короткое словесное описание,
   что этот ключ означает (например: `"meaning": "пресс, повторения"`).

3. **Определи, как новые данные относятся к старым.** Типичные отношения:
   - **A+B** — новое значение складывается из старого и нового кусков
     (сумма и расфасовка: одна общая цифра, из неё выделены части);
   - **A — подмножество B** — новое упражнение является усложнением или
     упрощением старого (то же движение, другая вариация);
    - отношения может не быть — тогда пустой массив.

4. **Реши, куда добавить новые ключи.** Если новые ключи расширяют существующее
   правило той же предметной области/упражнения (например, новая метрика `*_max_set`
   для уже описанных `push_reps`/`pull_reps`), укажи его точный `id` в
   `updateRuleId`. Если общего существующего правила нет или выбор неоднозначен,
   укажи `null`; не угадывай. История предыдущих версий сохраняется отдельно;
   текущий снимок описывает только активное правило после обновления.

   При непустом `updateRuleId` следуй контракту формирования снимка перед JSON.

   Для максимума за один подход используй точные ключи `push_max_set` и
   `pull_max_set` соответственно. Суффикс строго в единственном числе: `_max_set`,
   не `_max_sets`.

## Нейминг новых ключей (строго)

Ключ — только **латиница**, нижний регистр, формат `<группа>_<метрика>`:

- Никакой кириллицы. Никакого транслита. Только латиница.
- Короткие, но семантически понятные названия: по группе упражнений и метрике.
- Никаких безликих Type A, Type B, var1, var2 — по названию должно быть ясно,
  что это за упражнение и что за метрика.

Для терминов из пользовательского словаря используй канонические ключи:
`пресс` → `press_reps`, `присяд` → `squat_reps`, `бег в км` → `running_distance_km`.
В принятом пользовательском словаре «подтягивания на кольцах» — `pull_rings_reps`;
даже фраза «австралийскими отжиманиями на кольцах» внутри строки подтягиваний означает
`pull_rings_reps`, а не `push_rings_reps`. «Отжимания с колен» — `push_knees_reps`.
Не заменяй `press_reps` на `situp_reps`. Если входные правила уже содержат ключ
сущности, сохраняй его написание точно.

Роли ключей: **stack** — базовая полоска стека (сумма/основная метрика),
**overlay** — надстройка поверх базы (выделенная часть, максимум, отдельный
вариант, который рисуется поверх). Роль тренда здесь не назначается.

## Контракт снимка правила при обновлении

Если `updateRuleId` непустой, создай `rule.mapping` и `rule.examples` ЗАНОВО по текущему `{{INPUT}}`. НЕ КОПИРУЙ и НЕ ДОБАВЛЯЙ к ним исторические данные из `{{RULES}}`.

- `K_old` — ключи старых измерений текущего `{{INPUT}}`, распознанных по `{{RULES}}`.
- `K_new` — ключи новых измерений текущего `{{INPUT}}`; набор ключей `rule.keys` должен в точности равняться набору ключей `newKeys` (`K_new`).
- `rule.mapping` содержит ровно `K_old ∪ K_new`: meanings старых ключей можно взять из `{{RULES}}`; не включай ключи, не измеренные в текущем `{{INPUT}}`.
- `rule.examples` содержит ровно по одному примеру на каждую отдельную запись упражнения текущего `{{INPUT}}`, со всеми её старыми и новыми значениями. Объедини значения из `oldKeysEvents` и `newKeys` одной записи. `input` — точная подстрока этой записи; не включай примеры только из `{{RULES}}`, целый день или заголовок даты.
- Предыдущие версии остаются в истории отдельно. Если `updateRuleId` равен `null`, этот контракт не применяется: создавай правило по прежнему пути из новых ключей.

## Формат ответа (строго один JSON)
```json
{
  "status": "success",
  "payload": {
    "updateRuleId": "rule_001",
    "rule": {
      "keys": [
        { "key": "group_metric", "role": "stack", "meaning": "пресс, повторения" }
      ],
      "composition": "single | A+B | subset | max",
      "mapping": { "group_metric": "смысл метрики" },
      "examples": [
        { "input": "точный фрагмент отдельного упражнения", "values": { "group_metric": 7 } }
      ]
    },
    "oldKeysEvents": [
      { "key": "существующий_ключ", "chunk": "дословный кусок ввода",
        "values": { "существующий_ключ": 42 } }
    ],
    "newKeys": [
      { "key": "group_metric", "meaning": "пресс, повторения",
        "chunk": "точный фрагмент исходного упражнения",
        "values": { "group_metric": 7 } }
    ],
    "relations": [
      { "type": "A+B", "base": "push_reps", "parts": ["push_knees_reps"],
        "stackOrder": ["push_reps", "push_knees_reps"] },
      { "type": "overlay", "base": "push_reps", "sub": "push_max_set" }
    ],
    "confidence": 0.85
  },
  "confidence": 0.85
}
```

- `rule.keys` — ТОЛЬКО новые ключи (для старых данных правило не нужно), для
  каждого — `meaning`: кусочек смысла, что означает этот ключ (без дат).
- При непустом `updateRuleId` поля `rule.mapping` и `rule.examples` обязательны
  и задают полный актуальный снимок; при `updateRuleId: null` применяй прежний
  путь создания правила из новых ключей.
- `updateRuleId` — ID существующего правила для расширения либо `null`; не
  указывай ID, которого нет в {{RULES}}.
- `oldKeysEvents` — перевод старых кусков по существующим ключам; если старых
  кусков нет — пустой массив. Не добавляй дату: pipeline знает дату обрабатываемого
  дня и проставляет её отдельно.
- `newKeys` — новые ключи с дословным фрагментом исходного упражнения, смыслом
  (mapping) и распознанными значениями; примеры — формулировка + числа, БЕЗ дат.
- `chunk` — точная непрерывная подстрока `{{INPUT}}`, которая подтверждает именно
  это упражнение. Для связанных метрик одной записи (например, пары A+B) можно
  повторить один фрагмент упражнения у каждого ключа. Для разных упражнений
  укажи их отдельные фрагменты; не копируй весь день в качестве примера.
- Если подходящий фрагмент нельзя выделить дословно, пропусти `chunk`, но сохрани
  сам ключ и его `values`. Не пересказывай и не исправляй исходный текст.
- `relations` — отношения отрисовки (формат графа):
  - **A+B** — стек из полосок: `"type": "A+B"`, `"base"` — первая реальная
    составляющая A, `"parts"` — массив остальных составляющих B. Общий итог —
    контекст, а не отдельный ключ/полоска. `"stackOrder"` — порядок полосок
    **СНИЗУ ВВЕРХ** (сложное базовое движение, затем его варианты).
  - **overlay** — надстройка поверх базы: `"type": "overlay"`, `"base"` — полная
    метрика, `"sub"` — метрика, которая рисуется поверх (максимум, выделенная часть).
  - НИКОГДА не придумывай синтетические ключи вида `<группа>_total` — их нет в
    данных, и в relations их быть не должно. Связывай только реальные ключи.
- **raw передаётся дословно**: {{INPUT}} — полный ввод прогона; каждое указанное
  `chunk` — точная вырезка из него, ничего не перефразируй и не пересказывай.
- **Самопроверка полноты**: каждое измеряемое значение из ввода должно быть
  представлено ровно один раз либо в `oldKeysEvents`, либо в `newKeys`; для
  общего итога с указанными частями — только значения частей. Комментарии без
  измеряемых значений не превращай в ключи и сохраняй исходный ввод в `raw`.
