# Извлечённые знания из архивируемого/удаляемого кода

> 2026-09-01, инвентаризация под architecture.canvas (docs/user/artifacts/).
> Эти знания собраны из комментариев и устройства модулей, уходящих из живого
> кода при переходе на 3-веточную схему. Хранятся здесь, чтобы опыт не потерялся.

## Из core/interpreter.js (старый «двухпроходный автомат», из пайплайна не вызывается)

1. **«Слово первым» в правилах** — формат правила, читаемого LLM: имя упражнения
   идёт раньше числа (читаемость для модели и человека).
2. **Решение о трактовке — в интерпретаторе, НЕ в data/rules.json** — данные
   никогда не редактируются ради подгонки под код; логика живёт в коде, данные read-only.
3. Режимы 'resolve'/'ambiguous' как статусы решения (не LLM-вызовы): отбор
   «правила не сработали, но есть число + правдоподобный контекст → proposal»
   против «не покрыто вообще → требует контекст». Полезная градация отказов —
   пригодится Branch 3 (mode_RuleUpdate).

## Из core/rules.js (детерминированный движок match/propose/applyMigration)

1. **match() = эталон детерминированного ВЕРИФИКАТОРА, не распознавателя**:
   подтверждает/опровергает кандидата по структуре правила, но никогда не
   разбирает сырой ввод (ПАМЯТКА REQ-1). В новой схеме Branch 3 может
   переиспользовать именно эту дисциплину.
2. **applyMigration** — пакетная миграция правил одной транзакцией (используется
   rulesLog.appendRule при changeType='migrate'); семантика: старые события не
   трогаем, версия +=1, запись append-only.
3. SECONDARY_METRIC (push→knee, pull→assisted) — историческое знание о парных
   ключах (осн.+упрощ.), теперь живёт в данных графа (relations part_of).

   канон теперь — вокабуляр из rulesLog (extractVocabulary в core/structured.js).
   Урок: **один источник истины на сущность** — второй словарь неизбежно расходится.

   понижаться в грацию при отсутствии модуля (что делал), но модуль без
