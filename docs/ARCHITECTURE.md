## 0. Каноническая схема (по канве, 2026-09-01)

Актуализация старта 2026-09-26 по `docs/user/artifacts/architecture.canvas`
(узел `8ce01f0c60632959`): `ui/editor.js` восстанавливает три temp-файла через
Vault API и показывает main + temp, уведомление и кнопку отдельной очистки.
При рендере файлы не очищаются. Общий Save фиксирует восстановленный черновик;
повторная обработка очищает temp перед новым циклом. Если рендер произошёл
во время LLM-запроса, экземпляры виджета разделяют только статус операции;
после её завершения новый экземпляр перечитывает файлы. Данные остаются в Vault.

```
👤 Ввод rawData (поле 1, без побочных эффектов)
👤 «Обработать данные»
│
├─ 1. ROUTER — core/router.js + prompts/mode_router.md
│      Сравнивает вход с правилами ({{RULES}} = срез последних 2 правил:
│      реальные примеры из двух последних правил + номера правил,
│      доп. прочтения на ключи = примеры употребления кроме первого).
│      ДЕЛИТ ввод на куски и направляет по группам:
│        1. правило существует, вход попадает ПОЛНОСТЬЮ (пример в правиле) → Branch 1
│        2. правило существует, попадает с высокой уверенностью, формулировка отличная → Branch 2
│        3. в правила не вписывается → Branch 3
│      Детерминированная проверка: llmBranch() + semanticBranch() fallback (AC10)
│
├─ 2a. BRANCH 1 — «Добавление по правилам»
│      core/structured.js + prompts/mode_parse.md
│      Читает правила и вокабуляр из rulesLog ({{RULES}}) →
│      переводит ввод в готовый к отрисовке JSON ({date, values}).
│      Детерминизм = ТОЛЬКО структурная валидация после LLM (keyNaming, контракт).
│      → events → data.tmp.json (temp)
│
├─ 2b. BRANCH 2 — «Минорное дополнение правил»
│      prompts/mode_minorRuleUpdate.md  (⚠️ создать при реализации)
│      Сравнивает примеры из правил с примерами из данных, находит расхождения.
│      Подготавливает аппенд маппинга в rulesLog.tmp.json:
│      ключ → новый пример употребления.
│      После аппенда данные идут «добавление по правилам» заново (Branch 1,
│      уже с дополненным словарём).
│      → rulesLog.tmp.json (temp)
│
└─ 2c. BRANCH 3 — «Разрешение конфликта — придумать новое правило»
       core/conflict.js + prompts/mode_RuleUpdate.md  (⚠️ создать при реализации;
       сейчас Branch 3 переиспользует mode_parse.md через TRANSPORT_MODE='parse')
       mode_RuleUpdate.md должен уметь:
       - разделять данные: часть по старому правилу / часть под новые ключи;
       - подобрать новый ключ новому типу данных (нейминг: латиница, семантика,
         <группа>_<метрика> — цитата 2026-08-31);
       - определить отношения новых данных со старыми (A+B, A подмножество B).
       На вход: данные + последние правила отрисовки.
       → rulesLog.tmp.json + graph.tmp.json + data.tmp.json (temp)

── Сведение ──────────────────────────────────────────────
STAGED-превью: график и JSON = main-файлы + tmp-файлы
  (data.json + data.tmp.json; graph.json + graph.tmp.json; rulesLog.json + rulesLog.tmp.json)
  ДАННЫЕ ПОКА ЕЩЁ НЕ ТРОНУТЫ.
👤 Не удовлетворён → снова «Обработать» (tmp очищается, цикл заново)
👤 Удовлетворён → явное «Сохранить» = транзакция (D10):
  tmp дописывается в main, tmp-файлы очищаются.
```

## 2. Modes (adapters/llm.js)

Транспорт: `callLLM('parse')` → status `success`. Router грузит свой шаблон
напрямую через loadTemplate. При реализации Branch 2/3 — добавить отдельные
modes ('minorRuleUpdate'/'ruleUpdate' или эквивалент), чтобы шаблоны не путались.

## 3. Модули (кто что делает)

| Модуль | Роль |
|---|---|
| `core/pipeline.js` | Оркестратор: router → B1/B2/B3 → валидация → контракт для UI |
| `core/router.js` | Деление ввода на куски/группы (LLM + детерминированный fallback) |
| `core/structured.js` | B1: LLM-кандидаты → структурная валидация → события; `buildRulesTable()` — текст для {{RULES}} |
| `core/conflict.js` | B3: `proposeRule()` — предложение правила + пример-события (перевести на mode_RuleUpdate.md) |
| core/llmGateway.js | Единственная точка вызова LLM: loadTemplate → substitute → chat → validateResponse; [LLM]-логи |
| adapters/llm.js | Транспорт: POST Ollama (gemma4, /api/chat); mode→status; [LLM]-логи тела запроса |
| core/rulesLog.js | Лог правил (append-only, версии). getLatestRules() — источник {{RULES}} |
| adapters/tmpStore.js | Temp-слой: rulesLog.tmp/graph.tmp; mergeRuleSnapshots() (tmp_session_keys) |
| ui/editor.js | Перед «Обработать»: срез правил main ∪ temp; запуск pipeline.next; STAGED-превью |

## 4. Формат {{RULES}} (уточнение пользователя 2026-09-01)

Правило в rulesLog хранит: raw-ввод ОДИН раз на всё правило (базовый пример) +
маппинг по ключам (ключ → кусок текста, отвечающий за прочтение этого ключа).
В LLM передавать: основное правило как оно выглядело первоначально (raw, целиком,
один раз) + ТОЛЬКО разночтения по маппингу. Не дублировать базовый пример.
tmp_session_keys должен доезжать в том же формате (сейчас — пустая строка, дефект).

## 5. Известные дефекты живого кода

- `buildRulesTable` (structured.js) не печатает tmp-правило `tmp_session_keys`
  (нет when.pattern) → LLM видит пустую строку вместо ключей сессии.
- Router в коде возвращает branch 1|2 и не делит ввод на куски — несоответствие
  канве, устраняется при реализации.
- Хандофф-доки (docs/HANDOFF.md) — рабочий журнал сессии, источником знаний НЕ
  является; стабильные доки на него не ссылаются.
