## D8[agent]. LLM — первичный движок распознавания/перевода; правила — лог (релайнмент)

- **Дата:** 2026-08-29 ~15:31
- **Решение (ПЕРЕСКАЗ агента, НЕ авторитет пользователя; корректировка D4/D6):** суть приложения — «какие угодно недетерминированные данные → JSON; при необходимости → обновить правила отрисовки». **LLM — ПЕРВИЧНЫЙ движок** распознавания и перевода, НЕ детерминированный регекс-интерпретатор. Архитектурные слои (дословно по заказчику): `Semantic Interpreter (Router)` выбирает путь → **Branch 1** `Structured Event` (LLM: данные + последние правила из лога → готовый к отрисовке JSON) или **Branch 2** `Unknown/Conflict` (LLM: придумывает правило → пример-отрисовка на данных юзера) → **Rule Evolution** (принял → добавить в правила отрисовки).
- **Правила** — версионируемый **лог** (`data/rulesLog.json`), который `Structured Event` читает, `Rule Evolution` пополняет. Регекс допускается как быстрый путь, но маршрутизация и перевод — LLM.
- **Сильное сохраняется (из D4/D6/AC10):** события иммутабельны; LLM-кандидаты подтверждает интерпретатор; контракт LLM — `{status,payload,confidence}`; рендер — из графа.
- **Следствие:** миграция D6/D7 описывала механику (движок не подключён в рантайм — расхождения D1–D9). Фазы релайнмента P-A…P-Q в `docs/ROADMAP.md`; анализ — DISCREPANCIES_PLAN (v2, файл удалён 2026-09-01 при инвентаризации).

## D9[agent]. Роль детерминированного слоя: валидатор контракта + формат, НЕ фильтр по формату (supersede части D8/D4)

- **Дата:** 2026-08-29 ~20:33
- **Контекст:** живой прогон реальных данных из 13-й недели показал, что детерминированный `interpret()`/`match()` не покрывает реальный домен (`- 100 отжимания (макс за раз: 100)`, `~6км (боли в ноге)`, `100 отжимания одним подходом (43 в одной планке)`, `пресс`, `присяд`, `велосипед 2ч`) и поэтому **выбрасывает валидный результат LLM**. При этом сама LLM (gemma4) на тех же данных **автоматически создала новые сущности** (`пресс_reps`, `присед_reps`, `велосипед_duration`), подтвердив замысел заказчика.
- **Решение (точная роль детерминированного слоя, дословно по заказчику):** суть — перевод недетерминированных данных в **детерминированные** (→ движок визуализации). **Движок визуализации/рендера — детерминированный и гибкий** (декларативно из `graph.json`: part_of→стек, successor→линия, independent→линия, targets→бар). **LLM — когнитивный движок на этапах принятия решения**: на основе недетерминированных данных **выбирает**, какие детерминированные правила применить (слой правил, вычленение из голого текста), и переводит недетерминированное в **детерминированные куски алгоритмов** (entity, метрики, relations, правила отрисовки), на которых графический движок рисует.
- **Роль детерминированного слоя (переопределена):** НЕ «фильтр по формату, отбрасывающий неизвестное», а (а) **валидатор структуры контракта** (дата есть и валидна; values — объект с числовыми значениями; ключи — в формате `entity_metric`; уникальность дат/иммутабельность событий), (б) **контейнер детерминированного вывода** (события, entity, relations) для рендера. **Детерминизм решает, КАК структурно оформить и отрисовать, а НЕ ЧТО распознать.**
- **Исправление ловушки:** «LLM-кандидатов подтверждает интерпретатор по формату» — УДАЛЕНО (это и была причина: интерпретатор не знал реальных форм и выкидывал валидный LLM-результат). Вместо этого LLM-кандидат принимается, если проходит **структурную валидацию контракта** (дата+числовые values+entity_metric), а детерминированный слой лишь оформляет события и rules/relations. Новые сущности/правила/relations создаёт LLM, вносит в детерминированный формат (log/graph), пользователь подтверждает в UI (Rule Evolution).
- **Следствие:** AC10/INV-4 переинтерпретированы: LLM — источник РАСПОЗНАВАНИЯ (какие правила применить, какие сущности создать); детерминизм — источник СТРУКТУРЫ/ФОРМАТА и гарантия иммутабельности/консистентности. Рендер остаётся детерминированным и декларативным (граф). Полный текст принципа — `AGENTS.md` 🔴 ПАМЯТКА и `docs/REQUIREMENTS.md` §0.

## D11[agent]. Одинаковые записи ≠ одна сущность: различие через семантические правила и контекст

- **Дата:** 2026-08-30 00:35; **ПЕРЕПИСАНО 2026-08-30 15:41**
  интерпретацией агента, противоречащей замыслу, — удалена. Основание: **дословная цитата
  пользователя 2026-08-30** — `docs/user/quotes.md` («Настоящий смысл D11»); пользователь разрешил
  вносить её как цитату и опираться на неё. Единственная запись лога с основанием уровня [user].
- **Постановка пользователя (дословно, см. цитату):**
  1. **Короткая перспектива.** «Пользователь может по-разному записать одинаковые для кода сущности
     в короткой перспективе. Пример: 100 отжиманий (макс за раз: 100) — если максимум стабильно
     остаётся 100, то пользователю бессмысленно и дальше писать "макс-подход", и это по сути обычный
     подход, но для данных это всё ещё push_max_set. (Было бы странно, если бы пользователь занимался
     как обычно, а график бы резко начал вести себя так, будто пользователь откатился в прогрессе
     и перестал желать макс подходы.)»
  2. **Длинная перспектива.** «Пользователь может на длинной перспективе записать новую сущность так,
     как когда-то записывал старую. Представим: пользователь постепенно меняет упражнения, и в
     какой-то момент отжимания перестали быть обычными отжиманиями (например, он делает их стоя на
     руках). Чтобы каждый раз не писать "делаю стоя на руках", пользователь просто начинает писать
     "отжимания" — сократил запись для удобства. От системы ожидается, что, зная контекст предыдущих
     записей, она поймёт: новая сущность НЕ добавилась и старая НЕ вернулась — пользователь просто
     упростил себе запись.»
  3. **Правило оценки «усложнилась/упростилась».** «Если запись усложнилась — скорее всего, нужно
     искать изменения правил. Если запись упростилась — скорее всего, это одно и то же, просто
     пользователь нашёл более удобный способ записи одного и того же.»
  4. **Откат прогресса.** «Мы всегда запрашиваем не только последнее, но и предпоследнее правило:
     у пользователя в моменте мог немного откатиться прогресс, и ему понадобились старые метрики
     (бывает: переоценил возможности, резко перешёл на новую метрику, не тянет — откатился к старой).»
- **Решение (инженерное, на основании постановки):**
  - различие одинаковых по форме записей определяется СМЫСЛОМ из контекста последовательных записей
    (динамика значений + история правил), а не формой текста;
  - при запросе правил LLM получает срез последних правил, включающий предпоследнее
    (`formatRecentRules(2)`, D14), чтобы откат к старой метрике не трактовался как новая сущность;
  - «упростившаяся» запись → та же сущность (метрика продолжает историю, график не ломается);
    «усложнившаяся» → сигнал искать изменение правил (Rule Evolution);
- **Статус реализации:** частично (срез последних 2 правил в Router/Structured — есть; эвристика
  «усложнилась/упростилась» и контекстный анализ динамики — НЕ реализовано, задача).

## D12[agent]. «В одной планке» ≠ упражнение «планка»; текущий охват отрисовки — только руки

- **Дата:** 2026-08-30 01:28
- **Доменная терминология (критично для LLM-промптов, уточнение заказчика):** в контексте
  «отжимания одним подходом (N в одной планке)» слово **«планка» НЕ означает упражнение-удержание планки**,
  а означает **отжимания, сделанные за один подход/планку**. Это сущность `push` (отжимания), `N` —
  макс отжиманий в подходе (`push_max_set`); трактуется так же, как «макс за раз». Признак из данных:
  N — счётное число отжиманий, меняется между днями (43 → 17) → это измеримая метрика тренировки,
  а не статичное время удержания. «Планка» как отдельное упражнение — только если во входе явно слова
  «планка»/«планочка» как самостоятельная строка без «отжимания одним подходом».
- **Охват отрисовки (на этот момент):** визуализируются **только две группы для рук** — отжимания (`push`)
  и подтягивания (`pull`). Прочие сущности (пресс, присяд, велосипед и любые новые) распознаются и
  фиксируются в событиях (данные принимаются и сохраняются), но на график пока НЕ попадают, т.к. в
  `data/graph.json` нет правил отрисовки для них. Расширение на ноги/пресс — отдельная задача (вынести
  когнитивную/отрисовочную конфигурацию в централизованный каталог), НЕ сейчас.
- **Решение (по заказчику, «не сейчас»):** большого рефакторинга не делаем. Закрепляем в промптах
  (`mode_parse.md`, `mode_router.md`) доменную терминологию «в одной планке» (push-метрика) и честный
  охват отрисовки (только руки). Обновлённые промпты вшиваются в bundle на сборке.
- **Следствие:** граф отрисовки (`data/graph.json`) остаётся источником для рендера; новые сущности вне
  графа не визуализируются, но сохраняются. Полная расширяемость (ноги/пресс/велосипед) — будущая задача
  по централизации когнитивной части.

## D13[agent]. Правила обязаны хранить примеры «как семантика переводится в json» (критическое упущение, восстановление первичного замысла)

  (а) LLM в `{{TABLE}}` видит голый паттерн без образца «как выглядели данные» и не может надёжно
  соотнести/обновить правило на похожем входе; (б) сравнивать правила и обновлять их по факту данных
  нечем. Это прямое упущение первичного замысла заказчика: «в правилах должны присутствовать примеры
  того, как данные могут поступить и в каком виде, чтобы правила можно было сравнивать и обновлять».
- **Решение:** правило получает опциональное поле `examples: Array<{ input, date, values }>` —
  пример (сырой ввод, дата, получившийся json-результат), как семантика перевелась в json.
  Закрепление:
  - `confirmProposal` (Rule Evolution, Branch 2) кладёт `examples` из предлагаемого ввода/даты/результата;
  - авто-фиксация новой сущности на Save (D10) тоже пишет пример;
  - `buildRulesTable` ({{TABLE}}) выводит рядом с паттерном строки «пример: <input> → <values> (date)»,
    чтобы LLM при следующем прогоне видела и абстрактный паттерн, и конкретный образец.
  - Старые правила без `examples` остаются валидными (поле опционально).
- **Следствие (скорректировано 2026-08-30 16:29 по вердикту пользователя 👍):** механика ПОСТАВЛЕНА,
  но консистентность распознавания ПОКА НЕ ДОКАЗАНА: проведены только smoke-прогоны против реальной
  Ollama, целевого тестирования «правила с примерами улучшают согласованность распознавания» НЕ БЫЛО.
  Открытое сомнение пользователя: смущает создание абстрактного паттерна по дате. Тест = прогон одних
  и тех же входов до/после и сравнение стабильности ключей; результат — записать сюда.
- **Результат целевого теста (2026-08-30, tools/d13-consistency-test.js, реальная Ollama gemma4,
  10 входов × 5 прогонов × 2 режима, коммит a0abaab):** стабильность модального набора ключей
  A (с examples) = 100% (10/10), B (без examples) = 98% (9/10). Формально +2 п.п., НО это не
  доказательство пользы examples: в обоих режимах проблемный вход «пресс» (голое слово без числа)
  стабильно НЕ распознаётся (в A — 5/5 error, в B — 4/5 error + 1 success); все остальные входы
  100% стабильны в ОБОИХ режимах. Вывод: для типовых входов examples не влияют на стабильность;
  реальная проблема — голое имя упражнения без числа (gemma4 возвращает пустой payload/null-значение
  или ambiguous) — отдельная задача на промпт. Сомнение про дату СНЯТО: входы с датой и без дают
  одинаковый модальный ключ (push_full) в обоих режимах — дата не порождает абстрактный паттерн.
