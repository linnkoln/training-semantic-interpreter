# Аудит репозитория перед публикацией

Дата: 2026-09-26. База: коммит `00c4315` — `fix(pipeline): finalize staged Save and isolate personal state`.

Статус: первичная инвентаризация и план. Массовые удаления, переносы документации, переписывание истории и публикация не выполнялись. Этот документ описывает инженерные предложения; он не заменяет пользовательские источники.

## Цель и уже сделанное

Другой пользователь получает общую логику добавления данных и создаёт собственные события, правила, вокабулярий, граф и состояние интерфейса. Репозиторий содержит исходники, пустые стартовые шаблоны, тестовые эталоны и описания логики.

В коммите `00c4315` исключены рабочее состояние и личные архивные JSON; 15 ранее отслеживаемых файлов сохранены на диске и сняты только с учёта Git. Сборка использует `data/defaults/`, а не личные правила и граф. Проверены первый Save нового пользователя и независимость тестов от живого состояния: guard 383/383 в рабочем checkout, 383/383 в изолированном экспорте индекса, сборка 15/15 QA в обоих случаях. Отдельный [отчёт о переносимости](../testing/reports/2026-09-26-portable-state.md) фиксирует условия проверки.

Это ещё не готовность к публикации: ниже есть воспроизведённые проблемы переносимости документации и неразобранные исторические инструкции. Открытые расхождения модели и живая приёмка остаются в [отчёте Repair Map 10/12](../testing/reports/2026-09-26-branch2-save-temp.md).

Игнорирование рабочих JSON не решает проблему старых текстовых инструкций: уже отслеживаемые документы не исчезнут из Git от добавления в `.gitignore`. ## Подтверждённые находки

1. **Переносы строк ломают эталоны при checkout.** При `core.autocrlf=true` экспорт подготовленного индекса успешно собирается и проходит guard, но `tools/check_test_docs.js` выдаёт 18 ошибок: 12 несовпадений SHA-256 fixtures и 6 несовпадений текста reference JSON с Canvas. В текущих рабочих файлах эта проверка проходит. Scratch evidence: `work/portable-index-doc-check.log`. Предлагаемый следующий шаг — узкая `.gitattributes` для fixture/reference JSON и manifests с LF, затем повторная проверка экспортированного дерева. Содержимое пользовательских эталонов не менять и не пересчитывать хеши ради сокрытия проблемы.
2. **Регистр путей скрывает проблему на Windows.** В Git есть `docs/user/decisions.md`, а `docs/user/README.md` называет `DECISIONS.md`. На системе с чувствительностью к регистру это другой путь. Проверить все ссылки по именам из `git ls-tree`, включая Canvas. Изменение пользовательского содержания вынести отдельно; исправление регистра ссылки не должно менять смысл текста.
3. **Два представления архитектуры.** `README.md:32` и `docs/ROADMAP.md:31` продолжают описывать LLM как наблюдателя старого интерпретатора. В `docs/GOVERNANCE.md` уже отмечено противоречие раннего ROADMAP пользовательскому заданию. Текущие AGENTS и pipeline закрепляют LLM как распознаватель, детерминированный слой — как верификатор.
4. **Исторические команды выглядят действующими.** `docs/HANDOFF.md:27` требует, чтобы PM не писал код и делегировал через `delegate_task`, хотя заголовок маркирует документ историческим. `tools/build.js:17` содержит старый комментарий о запрете редактировать core/adapters. Эти указания не описывают текущую работу.
5. **Смешанные handoff и статусы.** `docs/ORCHESTRATOR_HANDOFF.md` содержит старые числа тестов, отдельные бюджеты, модели, недоступный workspace Hermes и несостоявшиеся review. Его верхний статус также предшествует текущему коммиту. `REQUIREMENTS`, `QA_TESTING`, ROADMAP и `NOTES.md` нельзя использовать как единую актуальную сводку выполнения.
6. **Устаревший prompting guide.** `docs/PROMPTING_GUIDE.md` пишет о двух текущих промптах и плановых Branch 2/3; в сборке сейчас шесть режимов. Утверждения о sampling и роли старого интерпретатора требуют проверки по коду, а не переноса в новые задания.
7. **Архив содержит ограничители входа.** `archive/EXTRACTED_KNOWLEDGE.md` описывает «слово первым» и старый детерминированный движок. В активных инструкциях нельзя превращать эти сведения в требование к произвольному пользовательскому вводу.
8. **Legacy-код нельзя удалить по названию.** `core/interpreter.js` и `core/rules.js` остаются в сборщике и экспортах; `rulesLog` использует пустые DEFAULT_RULES и applyMigration, другие модули и тесты имеют зависимости. Сначала построить карту вызовов, затем предложить конкретное удаление или сохранение.
9. **Evidence не везде переносимо.** Отчёты ссылаются на игнорируемый `work/`. Для публикации нужны воспроизводимые команды и, где необходимо, небольшие очищенные приложения с версией и provenance. Отсутствующие локальные трассы не объявлять опубликованным evidence.
10. **История содержит личное состояние.** Коммит `00c4315` удаляет его из текущего дерева; предыдущие коммиты сохраняют старые blobs. Remote сейчас не настроен. Публичная история требует отдельного решения.

В процессе подготовки появились `docs/testing/model-evaluation/` и `tools/validate_model_evaluation.cjs`, которых не было в проверяемом снимке. Они оставлены вне `00c4315`: на момент проверки отсутствовал `CASE_MANIFEST.json`, preflight возвращал ENOENT. Это отдельная незавершённая работа; не удалять и не исправлять её молча в ходе чистки. После завершения определить её место в актуальном тестовом наборе.

## Последовательность дальнейшей работы

### 1. Переносимость проверяемого дерева

Подготовить узкую `.gitattributes`, проверить точные Git-пути и окончания строк. Повторить build, guard и `check_test_docs.js` в новом экспорте HEAD/индекса без личных файлов; отдельно проверить ссылки на системе с чувствительностью к регистру. Выход — рабочая новая установка и проверки без зависимости от настроек автора. Не смешивать это с редактированием эталонов или расширением домена распознавания.

### 2. Аудит контекста и документации

Для каждого файла/раздела зафиксировать: источник, дата, актуальность, конкретное противоречие, ссылка на замену и предлагаемое действие. Приоритет: пользовательские источники → актуальные контракты/код/проверки; старые agent-пересказы не получают пользовательский авторитет автоматически. Противоречия внутри пользовательских источников собрать с точными фрагментами для решения пользователем.

Подготовить короткий индекс активных документов и проект изменений README/AGENTS/handoff. Для истории выбрать явный архив, который не загружается по умолчанию. Удаления проводить небольшими проверяемыми коммитами после классификации; не стирать user-источники и provenance.

### 3. Код и инструменты

Построить карту реальных вызовов legacy-экспортов, тестов и утилит. Отделить необходимую совместимость от неиспользуемых генераторов и старых экспериментов. Для каждого кандидата на удаление указать зависимости и проверку, которая подтверждает сохранение пользовательской логики. Правки распознавания и промптов оценивать отдельно от чистки репозитория.

### 4. Подготовка к GitHub

Подготовить инструкцию установки Obsidian/Dataview, загрузки bundle, подключения графиков и локальной модели; описать фактические зависимости и проверенные версии. Проверить привязку `main.js` и storage к `scripts/training`, параметры endpoint/model, создание папок в новом Vault, установку hooks. Решить вопрос лицензии и минимальных CI-проверок; сейчас LICENSE и `.github/` отсутствуют.

Просмотреть публикуемые документы и приложения на личные сведения. Для истории сравнить два варианта: отдельный публичный репозиторий из очищенного снимка с сохранением локальной истории либо согласованная очистка истории существующего репозитория. Сейчас не выбирать и не выполнять переписывание автоматически.

Готовность к публикации: один понятный вход в документацию; личное состояние отсутствует в публикуемом дереве и выбранной истории; fixtures неизменны и воспроизводимо проходят проверки; новый пользователь запускает ту же логику и сохраняет собственные данные; обязательные ограничения приёмки описаны честно. Создание remote, push и публикация — отдельный последующий шаг.
