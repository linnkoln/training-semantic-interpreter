## 0. Направляющий принцип (ПАМЯТКА) — перевод недетерминированных данных в детерминированные

> **REQ-1 — самый важный. Вход «какие угодно недетерминированные данные».**
> Суть: перевод недетерминированных данных в **детерминированные** (→ движок визуализации).
>
> - **LLM — когнитивный движок на этапах принятия решения**: на основе недетерминированных данных
>   **выбирает**, какие детерминированные правила применить (слой правил, вычленение из голого текста),
>   переводит недетерминированное в **детерминированные куски алгоритмов** (entity, метрики, relations,
>   правила отрисовки), на которых графический движок рисует.
> - **Детерминированный движок визуализации — гибкий и декларативный** (из графа: part_of→стек,
>   successor→линия, independent→линия, targets→бар). Он исполняет выбранный LLM алгоритм.
> - **Роль детерминированного слоя:** НЕ «фильтр по формату, отбрасывающий неизвестное», а
>   (а) **валидатор структуры контракта** (дата валидна; values числовые; ключи `entity_metric`;
>   уникальность дат, иммутабельность событий), (б) **контейнер детерминированного вывода** (события,
>   entity, relations) для рендера. **Детерминизм решает, КАК структурно оформить и отрисовать, а НЕ ЧТО распознать.**
> - **Запрещено:** детерминированный слой НЕ обязан знать конкретные формы ввода (`отжимания (A+B)`,
>   порядок слов, конкретные ключи) и НЕ должен отбрасывать валидный LLM-результат только потому, что
>   не покрывает формат входа. Новые сущности/правила/relations создаёт LLM и вносит в детерминированный
>   формат (log/graph); пользователь подтверждает в UI (Rule Evolution, D9[user]).
> - **Повторяющаяся ловушка:** налагать детерминированный регекс/фильтр по формату на недетерминированный
>   вход — БАГ недокрытия домена, а не «корректная неоднозначность» (зафиксировано в AGENTS.md, PROBLEMS.md).
> - **НЕДЕТЕРМИНИРОВАННЫЙ ВХОД НЕ СВОДИТСЯ К ФОРМАТУ ЗАПИСИ.** Пользователь может **одинаково записать
>   разные по смыслу сущности** («макс за раз: 100» может быть и максимальным подходом, и обычным подходом,
>   если максимум стабилен = 100 и смысла в отдельной метрике нет). Различие таких записей определяется
>   НЕ формой текста, а **семантическими правилами и их апдейтами (Rule Evolution)**: LLM выбирает/создаёт
>   сущность по СМЫСЛУ, а правило отрисовки фиксирует, что данная запись означает (например, что стабильный
>   «макс за раз: 100» — это обычный `_full`, а не отдельная `_max_set`-метрика). Правила правят распознавание,
>   а не наоборот.

## 1. Реестр требований (REQ)

Каждое требование индексировано и трассируемо. `Уровень` — насколько это уже достигнуто в коде.

| ID | Требование | Уровень |
|---|---|---|
| **REQ-1** | Пользователь вводит **какие угодно** (недетерминированные) данные в поле 1 | 🔴 плана (P-F), фундамент LLM-движка только в плане |
| **REQ-2** | Система распознаёт характер данных: Router-LLM сравнивает вход с правилами и **делит ввод на 3 группы кусков** (полное попадание / попадание с другой формулировкой / не вписывается → ветки 1/2/3) — это решает **LLM** (Semantic Interpreter), не жёсткий регекс. Первоисточник: `docs/user/artifacts/architecture.canvas` | 🔴 плана (переработка под 3 группы) |
| **REQ-3** | Branch 1: **LLM** (Structured Event) смотрит последние правила из лога и переводит данные в **готовый к отрисовке JSON** | 🟡 частично (structured.js есть; формат {{RULES}} — см. ARCHITECTURE §4) |
| **REQ-4** | Branch 2: **минорное дополнение правил** — LLM находит расхождения примеров правил и данных, готовит аппенд «ключ → новый пример употребления» в rulesLog.tmp.json. Branch 3: **LLM придумывает новое правило**; пользователю показывается пример применения на его данных (пример-отрисовка) | 🔴 плана |
| **REQ-5** | Rule Evolution: если пользователь принял → правило **дописывается** в правила отрисовки (лог) через temp-слой, фиксация на «Сохранить» | 🔴 плана (сейчас append минует temp) |
| **REQ-6** | Пользователь получает **превью**: график **и** обновление данных (поле 2) | 🟡 частично (график есть; превью-слой staging нет) |
| **REQ-7** | Пользователь **подтверждает**, что данные перенеслись правильно (явное «Сохранить») — только после этого пишется файл | 🟡 частично (см. INV-2: сейчас commit-on-add) |

## 3. Инварианты, которые НЕЛЬЗЯ ломать (INV) — проверяются автоматически

### Граница Save в текущей реализации (2026-09-26)

REQ-5/REQ-7 и UX-3 реализуются одним кликом «Сохранить данные»: он подтверждает
предложенные события, полные правила с примерами (включая минорные дополнения)
и граф. Отдельная кнопка принятия правила и карточка результата удалены; пример
применения виден в поле 2 и на графике. Ошибки и предупреждения остаются в статусе.
До Save меняются только временные файлы через Vault API. Save записывает
`data/training/data.json`, `scripts/training/data/rulesLog.json` и
`scripts/training/data/graph.json` в общей транзакции, очищая temp после успеха.
При отказе записи постоянные файлы откатываются, temp сохраняется для повторной
попытки. Нечитаемый temp блокирует Save. Проверки: `tests/requirements.test.js`
и `tests/save-all.test.js` (браузерный bundle + mock Vault, не live Obsidian).

### Восстановление временных файлов при рендере (2026-09-26)

Источник: `docs/user/artifacts/architecture.canvas`, узел `8ce01f0c60632959`
«Программа запущена», и текущая задача пользователя. Рендер читает main + temp
данных, графа и правил; при старте temp не очищаются. Поле 2 показывает события
от последней даты к первой, причём сохранённое событие имеет приоритет над temp
с той же датой (INV-3). Непустой temp включает уведомление на графике и кнопку
«Очистить временные файлы»; пустые файлы и одни UI-настройки уведомления не дают.
Общий Save сохраняет восстановленные данные, правила с примерами и граф.
Очистка temp не меняет main и настройки скрытых групп. Повторная обработка
по-прежнему очищает temp перед новым циклом (узел `b9739c0e46fc855a`).
Если Obsidian перемонтирует виджет во время запроса, новый экземпляр показывает
статус текущей операции, не допускает конкурирующий reset/Save и после завершения
перечитывает готовый temp из Vault. Проверки: `tests/temp-recovery.test.js`,
`tests/branch2-save-temp.test.js`, `tests/requirements.test.js` (bundle/mock Vault).

## 4. Гейт по требованиям (как проверить коммит)

1. `node --test "tests/**/*.test.js"` — **обязан быть зелёным** (механика + инварианты).
2. `node tests/requirements.test.js` — инварианты пользовательской логики (INV-1…5).
3. Для коммитов, затрагивающих UX: сверка с §2 (UX-1…3) и REQ-6/REQ-7.
4. Для коммитов релайнмента LLM: каждая новая ветка должна закрывать п.8 «целевая модель».

## 5. Целевая модель (кратко, для трассировки)

```
raw input → Cutter-LLM (выделить даты) → для КАЖДОГО дня отдельно и по порядку:
  Router-LLM (один день → одна из 3 групп, {{RULES}} = срез последних правил, D14[user]) →
   Branch 1: Structured Event (LLM + правила из лога) → JSON                [REQ-3]
   Branch 2: минорное дополнение правил → аппенд примера в rulesLog.tmp     [REQ-4]
   Branch 3: новое правило (LLM) → пример-отрисовка                          [REQ-4]
   → Rule Evolution: принял → дописать в правила отрисовки (через temp)      [REQ-5]
```
Первоисточник архитектуры: `docs/user/artifacts/architecture.canvas`.
Расшифровка с привязкой к коду: `docs/ARCHITECTURE.md`.

## 6. Процесс защиты (pre-commit)

Переносимость установки (уточнение текущей работы 2026-09-26): общая логика обработки и Save одинакова для разных пользователей; рабочий журнал правил, граф, данные и temp принадлежат отдельной установке и не отслеживаются Git. Пустые шаблоны `data/defaults/` служат только начальным состоянием сборки. Отсутствие личного журнала при старте означает пустое состояние в памяти и не создаёт файл; первый Save создаёт его с версией 1. Это сохраняет INV-2/INV-5. Проверки: `tests/portable-state.test.js` и первый Save в `tests/requirements.test.js`. Пользовательские тестовые fixtures остаются отдельными эталонами, не стартовым состоянием приложения.

- Комитит **только PM** (см. AGENTS.md); исполнители не коммитят.
- **Pre-commit хук** гоняет `npm run guard` = `node --test "tests/**/*.test.js"` (быстро). Если тесты красные — коммит блокируется (это и есть «не ломаем другое»).
- Для тяжёлого случая доступен `npm run guard:full` (тог же результат, явная команда).
