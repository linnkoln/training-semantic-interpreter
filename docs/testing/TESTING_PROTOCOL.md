# Протокол тестирования Semantic Training Interpreter

> Рабочий стандарт сквозной оценки: Gemma 4 и её промпты, все узлы передачи данных, temporary state, Obsidian UI/Vault, Save и граф.
> Исполняемый план живой проверки: [`OBSIDIAN_ACCEPTANCE_RUNBOOK.md`](OBSIDIAN_ACCEPTANCE_RUNBOOK.md). Покрытие и текущие пробелы: [`TEST_MATRIX.md`](TEST_MATRIX.md). Текущий handoff и пользовательские решения: [`../ORCHESTRATOR_HANDOFF.md`](../ORCHESTRATOR_HANDOFF.md).

## 1. Цель и авторитет источников

Проверяется полный путь от запуска виджета и raw input до чтения сохранённого результата после reload. Качество ответов Gemma 4 — главный фокус; модульные тесты и data-flow нужны, чтобы понять, на каком конкретно звене возникло расхождение.

Ожидания берутся из пользовательских указаний и пользовательской документации `docs/user/`, которая является источником истины. Архитектура задаёт порядок стадий. Specs TC-001 и TC-002 в `docs/testing/` — проверяемые тестовые артефакты; обновлять их, если они противоречат архитектуре или уточнениям пользователя. Не считать все прочие документы источниками истины.

Если пользовательские требования сами противоречат друг другу, указать точные пути/узлы и спросить пользователя; модель не решает конфликт самостоятельно. Исправление тестовых артефактов по уже данному пользователем разъяснению не требует отдельного вопроса.

Тестируем обычный добросовестный ввод одного пользователя. Не раздувать проверки искусственными пограничными случаями; проверять устойчивость к реальной вариативности Gemma и ошибки целостности данных, которые могут повредить пользовательское состояние.

## 2. Слои доказательств

| Слой | Проверяемое утверждение | Сильное свидетельство |
|---|---|---|
| A — Gemma/промпт | Модель верно интерпретирует пользовательский ввод и текущую версию правил | Сырой prompt/response, модель/версия, правила на входе, точный пользовательский oracle и сравнение |
| B — узел | Cutter, Router, ветки, валидаторы, storage и chart-model соблюдают контракты | Unit-тест + точные вход/выход узла |
| C — data-flow | Нет потерь, неверной маршрутизации и устаревшего словаря между стадиями и днями | Trace всех вызовов/переходов одного запуска |
| D — staging/Save | Main остаётся неизменным до Save; отказ/повтор безопасен; temp состояние корректно | Хеши файлов до/после preview, после Save/reload, плюс tests |
| E — Obsidian | Виджет, Dataview, ввод, статусы, граф и Vault API реально работают | Проверка в текущем Vault после штатного полного сброса, скриншоты и Vault snapshots |
| F — bundle | Obsidian исполняет свежую сборку с текущими кодом и prompts | `npm run build`, `npm run guard`, reload test note, build ID/hash |

Наличие тестового файла, строки в этой матрице или зелёного общего guard само по себе не закрывает каждый слой.

## 3. Якорные кейсы и поведение

- **TC-001** — пустые правила; сначала Cutter выделяет три даты, затем каждый день отдельно проходит Router: Branch 3 создаёт правило, Branch 2 дополняет пример, Branch 1 использует его. Полная фикстура ожиданий и значений: `cases/TC-001-empty-rules-table/TC-001-spec.canvas`.
- **TC-002** — две сохранённые версии правила и две связи A+B из TC-001; знакомые данные и ненулевые/нулевые компоненты плюс новые max-метрики. Полный эталон: `cases/TC-002-max-approaches/TC-002-spec.canvas`.

Полные конечные JSON для обоих кейсов находятся в `reference-data/TC-001/` и `reference-data/TC-002/` и дословно вставлены в соответствующие Canvas. Каждый день проходит отдельный цикл Router и выбранной ветки. Исторические core-прогоны, созданные до исправления формата `rulesLog` и накопления отношений `graph.json`, подтверждают только те значения и вызовы, которые совпадают с новым эталоном; их старые файловые снимки не считаются ожидаемым результатом Save.

Для чисел/ключей/групп сверять пользовательскую документацию и подтверждённые решения в handoff. Старые run reports и прежние тестовые Canvas — наблюдения, а не решения пользователя.

Разрешено извлекать регрессии из сохранённых пользовательских данных, если установлено происхождение данных. Сохранённый ответ модели — наблюдение, не новый эталон.

## 4. Трасса и локализация дефекта

Для каждого сквозного запуска сохранять run ID и trace ID; исходный input; Cutter days; каждый Router request/response; выбранную группу и dispatch; ввод/вывод Structured, MinorRuleUpdate и RuleUpdate; session rules до/после; события; graph relations/targets; preview; хеши main/temp; Save и reload результат.

Классифицировать первое расхождение как одно из:
- семантический ответ Gemma/промпт;
- недостающий/лишний вызов или неверная диспетчеризация;
- нарушенный контракт конкретного узла;
- потеря или изменение данных на границе узлов;
- неправильный staging/Save/очистка;
- UI/Vault/bundle;
- недостаточная трассировка.

Исправлять и перепроверять первое место расхождения, а не маскировать поздний симптом. Если trace не содержит поле, нужное для локализации, сначала добавить наблюдаемость и повторить в текущем Vault после штатного полного сброса.

## 5. Повторяемость Gemma и критерий результата

Для TC-001 и TC-002 выполнить три независимых прогона на чистых копиях соответствующего начального состояния:
- TC-001 — три копии empty-state fixture;
- TC-002 — три копии одного и того же чистого подтверждённого результата TC-001.

Каждый run получает отдельный ID и собственные сырые ответы. Никакого majority vote: расхождение между запусками — признак нестабильности, кейс не закрывается до анализа и исправления промпта/контракта. После каждой правки prompt/runtime повторить оба якоря и затронутые тесты. Неполный evidence предыдущих прогонов не считать 3/3.

Целевая модель — Gemma 4 через штатный локальный endpoint проекта. Зафиксировать endpoint, ID модели и digest/revision, если он доступен. Hermes/OpenRouter применим только для узкой вспомогательной задачи; его вывод не заменяет Gemma и не расходовать малый пользовательский баланс без нужды.

## 6. Изоляция и безопасность данных

Core/Gemma повторы выполняются из isolated scratch copies; живой UI/Vault этап проводится в уже существующем пользовательском Obsidian Vault — новый Vault не создавать. Для якорей использовать подготовленные fixtures; перед фактическими изменениями сравнить и сохранить snapshots/hash шести файлов: `data/training/data.json`, `scripts/training/data/rulesLog.json`, `scripts/training/data/graph.json` и соответствующих трёх temp-файлов. Для кейсов следовать пользовательскому сценарию и штатному управлению состоянием, затем проверить результат после reload.

Успешный Save — это отдельный шаг с явным кликом пользователя. До клика все main snapshots должны совпадать. После клика сверять данные, правила, отношения графа, версии и пустое temp-состояние. После reload проверить, что данные действительно читаются из Vault, а граф остаётся правильным.

Для Branch 2 кнопка «Принять правило» означает только человеческое одобрение черновика: сама кнопка не меняет ни один main-файл. Нажать Save после одобрения и проверить атомарную запись события/правила/графа. В отдельном прогоне сохранить событие без одобрения и убедиться, что предложение правила не попало в журнал. Branch 2/3 при браузерном выполнении должны подготовить новый rulesLog в памяти и передать его общему Vault Save; прямой `fs`-записи до Save быть не должно.

Fault-injection транзакции выполнять только на отдельной копии. Ошибка нескольких записей не должна приводить к незамеченному частичному состоянию; сохранить все файлы и способ восстановления.

## 7. Canvas и отчёты

Canvas используется для человеческой визуальной проверки и как зафиксированный визуальный oracle; он не обязателен для unit-test. Пользовательские Canvas не редактировать.

Соседние артефакты кейса:
- `*-spec.canvas` — эталон;
- `*-evidence.json` — сырые ответы/файловые снимки конкретного запуска;
- `*-run-report.md` — сравнение, first divergence, решения и статус.

Использовать `EXECUTION_REPORT_TEMPLATE.md`. Заполненный результат содержит trace, точные ожидаемые/фактические данные, снимки до/после Save и reload, screenshot preview и графа. Статусы `PASS`, `FAIL`, `BLOCKED`, `NOT RUN` ставить по evidence, не по памяти.

## 8. Обязательная последовательность перед закрытием

1. Прочитать `AGENTS.md`, handoff и правила governance; сверить пользовательские источники и текущие вопросы.
2. Проверить все 20 этапов по `TEST_MATRIX.md`; не принимать несуществующие тесты или статичные Canvas mock за live UI pass.
3. Выполнить unit/guard и build после последних source/prompt changes.
4. TC-001 и TC-002: три свежих per-day core-pipeline повтора каждого anchor выполнены и описаны в anchor reports. Не повторять без причины; для пользовательской приёмки отдельно пройти UI → preview → Save → reload → chart в текущем Vault.
5. В текущем Obsidian Vault после штатного полного сброса пройти input → run → preview → отказ/re-run → Save → reload → chart для обоих anchors.
6. Проверить восстановление `.tmp` при старте, уведомление/кнопку для непустого temp, общий Save после reload и отдельную очистку temp. Новый прогон по-прежнему очищает temp до обработки. Перемонтировать виджет во время LLM и проверить появление готового результата.
7. Проверить успешную транзакцию и отказ записи/recovery отдельно в текущем Vault, сохранив исходные копии JSON для возможного восстановления.
8. Убедиться, что нет пользовательских oracle-конфликтов; если остались — оставить соответствующие части `BLOCKED`, не завершать кейс.
9. Запустить `node tools/check_test_docs.js` для локальных ссылок, тестовых файлов, 20 строк матрицы, cited Canvas node IDs и SHA-256 fixture; затем `git diff --check`. Обновить matrix, evidence, reports и handoff.
