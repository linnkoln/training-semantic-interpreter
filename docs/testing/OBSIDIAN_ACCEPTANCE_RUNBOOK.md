# Практический сквозной план Obsidian для TC-001 и TC-002

> Это инструкция для следующего оркестратора с доступом к Obsidian. Не отмечать live/UI/Vault-гейт пройденным по Node-тестам или изолированному core-прогону.
> Актуальные решения перечислены в handoff и в §1 ниже. Поля из user-owned docs проверять по пользовательскому oracle, а не по реализации.

## 1. Подтверждённые пользователем oracle-решения

1. **Архитектура обработки:** сначала Cutter режет весь raw input на дни; затем каждый день по отдельности проходит Router и свою ветку; результаты и состояние передаются дальше в порядке дней. TC-001 и TC-002 machine specs должны совпадать с этим порядком.
2. **Правдивые данные:** пользовательский ввод — источник фактов. Оркестратор/модель могут показать противоречие и запросить разъяснение, но не выбирают решение вместо пользователя. Явный числовой ноль в известной паре сохраняется (`pull_rings_reps: 0` для `(50+0)`). Если в следующей записи компонента нет, не переносить ноль автоматически; отсутствие поля отличается от нуля и в контексте может означать новое правило.
3. **TC-002, 07-21:** сохранять `pull_reps: 50` и `pull_max_set: 6`; `pull_rings_reps` не добавлять, если компонент не указан. Новые max-связи после Save имеют тип `overlay`, который система выводит из контекста записи.
4. **Temp-файл событий:** использовать `data/training/data.tmp.json`, как указано в пользовательской архитектуре.
5. `docs/user/` — источник истины для пользовательских требований. `docs/repair-map.canvas` — вспомогательная карта, не источник, который может переопределять пользовательскую документацию.

## 2. Подготовка текущего Vault

1. Работать в текущем Obsidian Vault. Перед каждым новым кейсом или чистым повтором выполнить штатную кнопку «Очистить память (полный сброс)» и убедиться, что состояние готово к заданному кейсу.
2. Выполнять команды из текущего checkout, расположенного внутри этого Vault. Перед UI-проверкой выполнить `npm test`, `npm run build` и `node tools/check_test_docs.js`; записать число тестов, Build QA и SHA-256 `bundle.js`. `npm run guard` запускать только если по `package.json` это отдельный, а не дублирующий `npm test` набор.
3. Убедиться, что в текущем Vault включён Dataview и разрешены JavaScript queries. В рабочей заметке/виджете использовать:
   ```dataviewjs
   await dv.view("scripts/training/main", {})
   ```
4. Убедиться, что локальный Ollama доступен по `http://localhost:11434/api/chat`, а модель `gemma4` загружена. Сохранить `ollama list`/digest модели, если среда его показывает. Не использовать OpenRouter/Hermes как замену Gemma и не расходовать OpenRouter-баланс на якорный тест.
5. Проверить, что `scripts/training/main.js` читает `scripts/training/bundle.js`, а LLM вызовы действительно уходят на локальную Gemma. После сборки перезагрузить/переоткрыть рабочую заметку; сообщение о bundle/Dataview/Ollama ошибке — блокер запуска.

Пути в Vault:

- события: `data/training/data.json`;
- правила и постоянный граф: `scripts/training/data/rulesLog.json`, `scripts/training/data/graph.json`;
- временные события: `data/training/data.tmp.json`;
- временные правила/граф: `scripts/training/data/rulesLog.tmp.json`, `scripts/training/data/graph.tmp.json`;
- трассы: `data/test-artifacts/trace-*.json`.

## 3. Подготовка и приёмка TC-001

Для каждого независимого повтора выполнить штатный полный сброс в текущем Vault. Если сброс не приводит файлы к ожидаемому seed-состоянию, сверить их с фикстурами `docs/testing/fixtures/TC-001-empty-state/` и восстановить только нужные файлы; сопоставление и исходные SHA-256 приведены в README и `SHA256SUMS`. До начала теста сохранить копии/хеши трёх основных и трёх временных JSON. Ожидается: события пусты, `rulesLog.json` содержит `{"rules":[]}` без пустых версий, `graph.json` содержит `{"relations":[]}`, все temp пусты.

1. Открыть заметку и проверить стартовый экран: существующие события/граф отображаются без ошибок, поле JSON упорядочено от последней даты к первой, нет старого черновика.
2. Вставить дословный ввод из `docs/testing/cases/TC-001-empty-rules-table/TC-001-spec.canvas` (узел `input`) и убедиться, что ввод не меняет ни одного файла и не запускает LLM до кнопки.
3. Нажать «Обработать». Сохранить trace ID, все запросы/ответы, prompt versions, console output и снимки main/tmp. Сравнить Cutter, три отдельных вызова Router, Branch 3 → Branch 2 → Branch 1, staging и chart preview с узлами `router`, `cycle-1`…`cycle-3`, `staged` в спецификации.
4. Согласно подтверждённой пользователем архитектуре проверить группы `[3,2,1]`: 05-29 создаёт правило, 05-31 дополняет примеры, 06-02 использует дополненное правило. Проверить все 3 даты и ровно эти значения:

   | Дата | Ожидаемые значения |
   |---|---|
   | 2026-05-29 | `press_reps:50`, `squat_reps:50`, `push_reps:20`, `push_knees_reps:30`, `running_distance_km:5`, `pull_reps:5`, `pull_rings_reps:20` |
   | 2026-05-31 | `press_reps:50`, `squat_reps:50`, `push_reps:10`, `push_knees_reps:40`, `running_distance_km:5`, `pull_reps:3`, `pull_rings_reps:22` |
   | 2026-06-02 | `press_reps:50`, `squat_reps:50`, `push_reps:11`, `push_knees_reps:39`, `running_distance_km:5`, `pull_reps:3`, `pull_rings_reps:22` |

   Суммы 50/25 — контекст пользователя, они не становятся отдельными ключами. Комментарий о боли 05-31 не попадает в values. Никакого другого значения/ключа не выводить из формы текста.
5. До Save сверить поле 2 и граф: на экране — все три staged-события; две A+B-связи для push и pull, базовая компонента снизу. Сравнить хеши `data.json`, `rulesLog.json`, `graph.json` с состоянием до прогона: они не должны измениться до клика «Сохранить данные».
6. Нажать «Сохранить данные». Сверить три полных JSON в узлах `final-data`, `final-rules`, `final-graph` и в `docs/testing/reference-data/TC-001/`: три события, две непустые версии правила с пятью и семью примерами, две A+B-связи. Все временные события/правила/связи очищены. Перезагрузить заметку и убедиться, что данные, правила и граф читаются из Vault, а не только из runtime-кэша.
7. Сохранить скриншоты preview и после Save, снимки всех файлов, trace и заполненный отчёт. Никакие расхождения не исправлять через ручное редактирование эталонного результата.

## 4. Подготовка и приёмка TC-002

Перед TC-002 в текущем Vault подготовить его предусловия через успешное выполнение TC-001 либо сверить и восстановить нужные данные по fixture `docs/testing/fixtures/TC-002-after-TC-001/`. Её основные файлы побайтно совпадают с `docs/testing/reference-data/TC-001/`: две непустые версии правила с примерами, две A+B-связи и три события от позднего к раннему; все temp очищены. Фикстура **не доказывает live TC-001 Save**. Проверять SHA-256 перед восстановлением.

Ввести текст дословно из `docs/testing/cases/TC-002-max-approaches/TC-002-spec.canvas` (узел `input`), затем выполнить и зафиксировать те же уровни трассы, файловые snapshots, поле 2, preview и Save, что в TC-001.

Подтверждённые части ожидания:

- Router-группы `[1,1,3]`: 07-17 и 07-19 проходят **два отдельных цикла** Branch 1 с отдельными вызовами Router; новая max-величина 07-21 — третий цикл Branch 3.
- 07-17: `press_reps:100`, `squat_reps:100`, `push_reps:100`, `push_knees_reps:0`, `running_distance_km:10`, `pull_reps:36`, `pull_rings_reps:14`.
- 07-19: `press_reps:100`, `squat_reps:100`, `push_reps:100`, `push_knees_reps:0`, `running_distance_km:10`, `pull_reps:50`, `pull_rings_reps:0`.
- 07-21: `press_reps:100`, `squat_reps:100`, `push_reps:100`, `running_distance_km:10`, `pull_reps:50`, `push_max_set:32`, `pull_max_set:6`. Не добавлять отсутствующие компоненты и не переносить прежние нули.
- До Save main data/rules/graph остаются побайтно прежними; preview показывает новые события и визуально верные стеки/overlay согласно пользовательскому решению.
- После Save журнал содержит версии 1, 2 и 3. Версии 1 и 2 со всеми примерами сохраняются; актуальная версия 3 содержит новые max-метрики без ушедших knees/rings. В `graph.json` остаются обе прежние A+B-связи и добавляются два отношения `overlay`. Сверить полные файлы с узлами `final-rules`, `final-graph`, `final-data` в TC-002 Canvas и `docs/testing/reference-data/TC-002/`.
- После перезагрузки сведения берутся из постоянных файлов Vault; временные файлы пусты.

## 5. Проверка остального конвейера и критерий закрытия

Якоря покрывают главные семантические маршруты. Для всех этапов 01–20 выполнить строки `docs/testing/TEST_MATRIX.md`; каждый результат отмечать по факту `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`. Положительный unit/mock-тест не закрывает UI-путь. Отрицательный результат локализовать по первому неверному trace-шагу.

Отдельно проверить пользовательские петли:

- проверить восстановление непустых temp при старте в текущем Vault (процедура ниже), уведомление на графике и кнопку «Очистить временные файлы». Проверить, что файлы при старте не изменились;
- после preview нажать «Обработать» повторно: старый staging и временные правила/граф удалены до нового вызова, main-файлы прежние;
- после preview закрыть/переоткрыть: черновые события, правила и граф восстановлены, main не изменён; нажать Save и проверить фиксацию всех трёх слоёв;
- перерисовать заметку во время LLM-запроса: новый виджет показывает статус, второй цикл/Save/очистка блокируются до завершения, затем готовый результат появляется в новом поле 2 и графике;
- для Branch 2/3 и смешанного прогона проверить единое подтверждение: дополнительной карточки результата и кнопки «Принять правило» нет. До Save main snapshots неизменны; один клик «Сохранить данные» фиксирует события, полное правило с примерами, минорные аппенды и граф. При сохранении показывается путь журнала. Без клика Save постоянные файлы не меняются;
- для Branch 2 и Branch 3 проверить, что browser bundle готовит log/graph в памяти, все изменения проходят через Vault-транзакцию Save, а `rulesLog.json` не меняется до клика Save;
- проверить успешный Save, перезагрузку и отсутствие дублей при повторном открытии;
- после TC-001 и TC-002 проверить весь графический UI: сверить количество и состав графических панелей с уникальными сущностями/отношениями в сохранённом `graph.json`; каждая сущность должна отображаться один раз, даже если одновременно участвует в `part_of`, `A+B` и `overlay`. Нажать каждый checkbox упражнения отдельно и проверить, что фильтр меняет видимость серий существующего графа без перестройки данных, потери серий или создания повторных панелей. После нескольких переключений снова сверить снимок экрана и series с `graph.json`. По присланным пользователем скриншотам прежнее «дополнительное окно» означает повторные графические панели внутри виджета, а не отдельное окно Obsidian/браузера;
- в текущем Vault воспроизвести отказ по очереди на каждом из трёх main-файлов (`rulesLog.json`, `graph.json`, `data.json`): в mock `app.vault.create/modify` записывать вызовы, изменить содержимое выбранного файла и затем один раз бросить ошибку (моделировать частичную запись). После ошибки ожидаются: все три main-файла побайтно прежние, staged/temporary предложения не потеряны, UI ясно показывает Save failure. Затем снять отказ и нажать Save повторно: изменения применяются ровно один раз, дубликатов событий/примеров нет, temp очищены. Перед live fault-injection записать исходные копии/хеши файлов, чтобы при необходимости восстановить их вручную. Если rollback не восстановил все main-файлы, temp уничтожены или повтор удваивает данные — это `FAIL` и дефект транзакции/recovery, не закрывать пункт.

### Подготовка отдельного startup-temp recovery прогона

Запустить отдельно от TC-001/TC-002 в текущем Vault: штатным полным сбросом очистить состояние, затем до открытия заметки заполнить три temp-файла пробными данными ниже.

`data/training/data.tmp.json`:

```json
{
  "events": [
    { "date": "2026-09-03", "values": { "press_new": 40 } }
  ],
  "state": { "hiddenGroups": ["push"] }
}
```

`scripts/training/data/rulesLog.tmp.json`:

```json
{ "rules": [{ "id": "rule_001", "raw": "пресс 40", "mapping": { "press_new": "пресс" }, "examples": [{ "input": "пресс 40", "values": { "press_new": 40 } }] }], "newKeys": [] }
```

`scripts/training/data/graph.tmp.json`:

```json
{
  "relations": [{ "type": "part_of", "parent": "press", "child": "press_new" }]
}
```

Снять байтовые копии/hash трёх main и трёх temp-файлов. Открыть или перезагрузить заметку без нажатия «Обработать» и без LLM-вызова. Ожидается: все файлы побайтно прежние; поле 2 содержит событие 2026-09-03, граф показывает `press_new:40` по временной связи; появляется уведомление о временных файлах и кнопка их очистки. `state.hiddenGroups` остаётся `["push"]`.

Нажать «Сохранить данные»: событие, правило с примером и связь переходят в main, три temp пусты, уведомление и кнопка исчезают. Повторить подготовку и вместо Save нажать «Очистить временные файлы»: основные JSON побайтно прежние, события temp пусты, правила temp — `{ "rules": [], "newKeys": [] }`, граф temp — `{ "relations": [] }`, UI state сохранён. При пустых temp (включая файлы нулевой длины) уведомления нет. Зафиксировать UI и snapshots; event temp path — `data/training/data.tmp.json`.

План закрыт только после того, как:
1. подтверждённые oracle из §1 отражены в expected/actual comparison; любые новые противоречия остановлены и разрешены пользователем;
2. каждый этап матрицы получил результат и ссылку на свидетельство;
3. оба якоря прошли по целевому Gemma пути на трёх независимых чистых клонах без необъяснённых семантических расхождений (если модель дала разный ответ — сохранить все ответы и оставить кейс не прошедшим, не голосовать большинством);
4. оба кейса прошли UI → Vault → reload → видимый график в текущем Vault;
5. `npm run build`, `npm run guard`, чек свежести bundle и `git diff --check` прошли после последнего исправления.

## 6. Формат записи прогона

Для каждого запуска сохранить: case/run ID; дату/время; текущий Vault; build ID и bundle hash; модель/версию; версии или hash промптов; исходные fixture hashes; правила/граф/data до запуска; trace ID и вход/выход каждого узла; router-вызовы и группы; предупреждения/console; таблицу expected/actual; preview screenshot; main/tmp после preview; main/tmp после Save; результат reload и screenshot графика; итог и первый шаг расхождения.

Шаблон отчёта: `docs/testing/EXECUTION_REPORT_TEMPLATE.md`. Evidence хранить рядом с соответствующим case. Не помещать данные пользовательского Vault или секреты endpoint в репозиторий.
