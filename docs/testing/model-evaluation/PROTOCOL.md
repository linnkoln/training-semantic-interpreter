# Автоматическая оценка локальных моделей

Версия: 2. Дата: 2026-09-27. Статус: реализован последовательный исполнитель core-матрицы Ollama для TC-001/002 с независимыми процессами, проверкой preview, изолированной сериализацией и пакетами рецензии. Независимые snapshot-тесты всех стадий, llama.cpp transport и автоматическое подключение judge пока не реализованы. Числовые пороги скорости и бюджет адаптации ниже являются предложениями, а не новыми пользовательскими требованиями.

## 1. Что сравниваем

Единица сравнения — **модель + точные веса/quant + сервер + настройки каждой стадии + комплект промптов**. Результат Qwen с одним профилем не переносится автоматически на другой quant, thinking или backend.

Цель: получить корректные события и изменения правил на произвольном пользовательском вводе с меньшим временем ожидания и измеримой стоимостью адаптации. Вход распознаёт модель. Проверяющий код сравнивает результат и инварианты; он не превращается в распознаватель разрешённых форм ввода.

Этот протокол дополняет [общий протокол](../TESTING_PROTOCOL.md). Его scope — ответы моделей, промпты и core-цикл. Успешная оценка модели не закрывает живую приёмку Obsidian, Save/reload и визуального графа из [runbook](../OBSIDIAN_ACCEPTANCE_RUNBOOK.md).

Живые сравнительные прогоны выполнять отдельной явно запущенной командой evaluator. Не добавлять загрузку моделей и массовые LLM-вызовы в обычный `npm test` или commit guard: обычная регрессия кода и эксперименты над моделями имеют разные задачи и длительность.

## 2. Исходные данные и неизменяемые эталоны

Авторитет: `docs/user/` и текущие пользовательские решения; далее — якорные specs и [полные reference JSON](../reference-data/README.md). Реестр [CASE_MANIFEST.json](CASE_MANIFEST.json) содержит пути и SHA-256 текущего снимка. Подмена файла после регистрации означает новый снимок набора, а не прежний run.

В старых `*-evidence.json` использовать только поле `input`, сверенное с источником кейса. Старые ответы, `initialRules`, prompt versions и статусы оттуда не задают новый oracle. Для начального состояния использовать отдельные fixtures; для финала — reference-data.

| Кейс | Чистое начальное состояние | Ожидания |
|---|---|---|
| TC-001 | [TC-001-empty-state](../fixtures/TC-001-empty-state/README.md): события, правила и graph пусты | Три дня 05-29, 05-31, 06-02; Router `[3,2,1]`; семь исходных метрик; две непустые версии правила; две связи A+B. |
| TC-002 | [TC-002-after-TC-001](../fixtures/TC-002-after-TC-001/README.md): зафиксированный правильный результат TC-001 | Три новых дня 07-17, 07-19, 07-21; Router `[1,1,3]`; сохранение старых событий и версий; max 32 и 6; два новых overlay поверх прежних A+B. |

Контрольные значения для локализации ошибок:
- TC-001: 05-29 push 20/30 и pull 5/20; 05-31 push 10/40 и pull 3/22; 06-02 push 11/39 и pull 3/22. Остальные значения брать из полного oracle.
- TC-002: 07-17 push 100/0 и pull 36/14; 07-19 push 100/0 и pull 50/0. На 07-21 `push_max_set=32`, `pull_max_set=6`, `pull_reps=50`; ключи `push_knees_reps` и `pull_rings_reps` отсутствуют, а не равны нулю.
- В конечном `data.json` последние даты идут первыми, поля события — `date` и `values`. В staged/runtime-представлении могут существовать служебные поля: проверять их соответствующий контракт, но не добавлять их в внешний oracle.
- В актуальной версии правила TC-002 отсутствуют ушедшие вспомогательные метрики; прежние версии сохраняются. В graph остаются прежние A+B и новые overlay; persisted `targets/trends` не требуются и не допускаются oracle.

Не заменять пользовательский эталон успешным ответом кандидата или базовой Gemma. Противоречие в пользовательских источниках помечается `ORACLE_CONFLICT`; останавливается только зависящая от него проверка.

## 3. Три типа запуска

### A. Изолированные стадии

Выполнять Cutter, Router, Structured, MinorRuleUpdate и RuleUpdate на заранее зафиксированных корректных входных состояниях. Router проверяет один полный день с соответствующим словарём; присутствуют обычный Router и RouterSession для временных правил.

Для каждой записи хранить case/stage ID, raw input, полный входной словарь, ожидаемый контракт, источники ожиданий и хеши. Подготовленные входные состояния получают происхождение `reference-derived`; сохранённые состояния от неудачной модели — `observed`, их нельзя молча считать эталонными. Snapshot-набор всех стадий предстоит сформировать и проверить перед массовым прогоном.

Ответ оценивается до любых исправлений и после штатного парсера отдельно: `rawFormatPass` и `adapterContractPass`. Если штатный парсер уже поддерживает ограждения JSON, это не ошибка само по себе. Специальное исправление ответа новой модели становится версионированной частью профиля и считается дополнительной стоимостью; исходник сохраняется.

Эти тесты объясняют, какую именно стадию модель не тянет. Они не подтверждают работу накопления правил.

### B. Полный независимый core-цикл

Каждый repeat начинается в отдельном процессе и каталоге с чистой fixture. Весь кейс проходит Cutter → Router дня → выбранную ветку → обновлённый временный словарь → следующий день. Правила между днями берутся **из фактических ответов этой модели**, без подстановки исправленного эталона. Не менять день на правильный при ошибке предыдущего.

Для сравнения моделей TC-002 всегда начинает с одной и той же подтверждённой fixture TC-001. Дополнительный режим `chain` запускает TC-002 на фактическом успешном результате кандидата TC-001; его оценивать отдельно, без смешивания с результатами одинакового стартового состояния. При ошибке TC-001 цепочка не имеет статуса PASS.

Core-preview проверяется по ожидаемым новым событиям и предложениям. Полные persisted файлы проверяются только на отдельном этапе сериализации/Save в изолированной копии. Отсутствие Save не даёт права объявить конечный `rulesLog.json` прошедшим проверку. Для такого этапа можно использовать проектный Save-путь с mock/scratch storage и сохранением всех промежуточных снимков; это не live Vault acceptance.

### C. Переносимость на другие записи

Дополнять набор реальными пользовательскими фрагментами с известным происхождением и независимыми ожиданиями. Формы, комментарии, даты, числа и смысловые связи сохранять. Разделить записи для адаптации и закрытый контроль до начала адаптации; примеры контрольного набора не давать оптимизатору промптов.

TC-001/002 уже многократно использовались в prompt-lab: это regression/development anchors, **не независимый закрытый контроль**. Два якоря не доказывают понимание всех произвольных данных. Набор девяти дней добавлять после фиксации конкретного input и его ожидаемого результата; автоматически придумывать oracle нельзя.

## 4. Автоматические проверки

| Область | Проверка | Результат при расхождении |
|---|---|---|
| Транспорт | Ошибка сервера, таймаут, отмена, обрезка контекста/вывода, finish reason | `TRANSPORT_FAIL` / `TRUNCATED`; не подменять семантической ошибкой. |
| Контракт | JSON, обязательные поля, типы, допустимый status, ровно одна Router-группа дня | `CONTRACT_FAIL`. JSON Schema оставляет новые разрешённые metric keys открытыми. |
| Нарезка | Число и порядок дней, даты, сохранение исходных фрагментов и комментариев | `CUTTER_FAIL`; сравнение с известным входом кейса, не regex-фильтр реального домена. |
| Router | `[3,2,1]` / `[1,1,3]`, один вердикт на день, правильная ветка | `ROUTER_FAIL`. |
| События | Точные даты, наборы ключей и значения; ноль отдельно от отсутствия | `EVENT_FAIL`. Нет усреднения ошибок по полям. |
| Правила и примеры | Версии, обязательные ключи, накопленные examples и их значения, исходные text spans, отсутствие потерь старых версий | `RULE_FAIL`; правила по каждому snapshot сравниваются, не только последняя версия. |
| Graph | Тип и направление связи, base/parts/sub, stackOrder, сохранение прежних отношений | `GRAPH_FAIL`. |
| Состояние | Чистый старт, сохранность main до Save, неизменность старых событий, отсутствие влияния прошлого repeat | `ISOLATION_FAIL` / `INVARIANT_FAIL`. |
| Полнота | Ожидаемый день/стадия не выполнены, warning, частичный результат при `success` | `INCOMPLETE`. Пропущенная стадия не считается PASS. |

Сверять JSON структурно: порядок свойств объекта незначим; порядок дней/версий/stackOrder значим. Перестановка допустима лишь для явно объявленного множества. Не удалять неизвестные поля, не округлять числа и не заменять `null`/отсутствие/0, чтобы добиться PASS.

Для времени Save допускается отличие значения timestamp, если это предусмотрено reference README; проверять наличие/формат и порядок версий. Списки исключений для runtime IDs и иных служебных полей фиксировать **до прогона** и обосновывать контрактом. Не вводить новую нормализацию после просмотра неудачного ответа.

Текущий точный oracle mapping/examples сохраняется. Например, `пресс` вместо `повторения пресса` может получить отдельную смысловую оценку, но обязательная точная проверка продолжит показывать расхождение. Только отдельное изменение политики ожиданий может разрешить такую эквивалентность, с явным основанием и новым хешем набора.

## 5. Оценка моделью-рецензентом

Рецензент получает [JUDGE_PROMPT.md](JUDGE_PROMPT.md), исходный текст, полный словарь до стадии, пользовательский критерий, ответ кандидата и детальный автоматический diff. По возможности скрываются имя кандидата, производительность и самооценка confidence. Для спорных сравнений A/B менять порядок показа; judge prompt, модель/версия и настройки сохраняются.

Что проверяет рецензент:
- сохранён ли смысл количества/компонент/максимума и единиц;
- есть ли у ключей и новых правил основания во входе и текущем словаре;
- не изобретены ли упражнение, связь, значение или пример;
- различены ли новая форма записи и новое измерение;
- эквивалентны ли свободные словесные описания и насколько правило излишне сужено под виденный пример;
- где первое причинное расхождение и связан ли дефект с моделью, prompt, сборкой контекста либо контрактом.

Рецензент не переписывает вход/ответ/oracle и не снимает автоматический FAIL. Выход — конкретные observations с цитатой фрагмента, путём JSON, ссылкой на критерий, severity и `pass/fail/uncertain`. Нет единого впечатления «8 из 10»: числовой результат, точный oracle и семантический verdict остаются отдельными.

Ответ кандидата — данные для анализа, не инструкции рецензенту. Два прохода одним рецензентом не считать независимыми экспертами. Расхождение judge/автопроверки, неясный пользовательский смысл и judge=`uncertain` передаются для проверки, без автоматического majority vote. На новых контролях предпочтительна проверка агентом/пользователем всех критических расхождений; confidence самого кандидата не считается доказательством.

Чтобы оценить самого judge, хранить небольшой набор заранее разобранных правильных и неправильных ответов с известной причиной. Не использовать judge в качестве единственного критерия отбора, пока не проверены его решения на таком наборе. Доступ к внешнему платному endpoint не включается автоматически; можно оценивать сохранённые пакеты в этой задаче либо использовать явно настроенную локальную модель.

Обоснование вспомогательной роли judge: исследование [LLM-as-a-Judge](https://arxiv.org/abs/2306.05685) описывает, в частности, смещения по позиции, многословию и собственным ответам. Эти ограничения учитываются в дизайне, а не компенсируются объявлением judge источником истины.

## 6. Порядок сравнения и адаптации промптов

**Раунд 0 — переносимость.** Одинаковые текущие инструкции и fixtures. Каждой модели разрешён правильный нативный chat template и явно зафиксированный runtime-профиль: thinking, sampling, context, max output. Тексты задания и требования не меняются. Это сравнение готовых конфигураций; его нельзя назвать контролируемым эффектом только весов, если настройки различаются.

**Раунд 1 — целевая адаптация.** Если найден дефект, создать отдельный prompt-set кандидата. Смысл задания, output contract, примеры из development-набора и oracle сохраняются; разрешены порядок/подача инструкций, разделение system/user, краткость и штатные средства управления reasoning. Фиксировать diff, гипотезу, затраченное время и число проб. Production prompts не перезаписываются.

Ограничение для первого отбора: максимум две осмысленные итерации адаптации на кандидата, затем решение продолжать/отсеять по evidence. Это предложенный бюджет, не запрет дальнейших исследований. Внутри итерации менять одну гипотезу и проверять оба якоря. Глобальное отключение thinking не делать обязательным: прошлый probe показал Gemma 3/6 и Qwen 6/6 только на Router.

**Раунд 2 — замороженная проверка.** Зафиксировать профиль/промпты и провести три независимых core-прогона каждого якоря. Любая правка prompt/runtime после результата создаёт новую конфигурацию. Затем использовать закрытый контроль; если его результаты стали материалом для очередного изменения, этот набор перестаёт быть закрытым контролем.

Не менять компаратор, corpus, контекст и prompt одновременно ради зелёного результата. Исправление обнаруженного дефекта самого evaluator версионировать; affected результаты перепроверить отдельно и не выдавать за улучшение модели.

## 7. Повторяемость, время и ресурсы

- Smoke: один проход для поиска грубого дефекта, без вывода о стабильности. Qualification: три независимых чистых прогона каждого якоря согласно общему протоколу, без majority vote. Три повтора на двух кейсах не дают надёжную общую оценку частоты ошибок.
- Повторы не используют сохранённый ответ. Записывать seed, если backend его поддерживает; фиксированный seed/temperature=0 не объявлять гарантией детерминизма. Вариации seeds — отдельный эксперимент, не способ выбрать удачный ответ.
- Обработка дней внутри core-run последовательная; во время сравнительного измерения на одном GPU запускать одну измеряемую конфигурацию за раз. Judge выполняется после замеров, чтобы не занимать GPU кандидата.
- У каждого call: wall time, load/prefill/decode time, input/output tokens, доступный thinking count или хотя бы длина trace, finish reason, retries, полный prompt, сырой ответ, эффективные настройки. Не смешивать символы thinking с количеством токенов.
- На уровне run: число вызовов и повторов, wall time до первого результата, время до **полного правильного** результата, ошибки и стоимость повторных неудач. Отдельно холодный запуск, прогретый запуск и переключение моделей. Ошибочные быстрые runs остаются в таблице качества/ресурсов; latency успешных runs показывается с их количеством.
- Снимать модельные и общие VRAM, offload CPU/GPU, runtime/driver version и конкурирующую нагрузку. Не освобождать другие пользовательские процессы ради хорошей цифры.
- Для трёх повторов показывать каждое время, median и max. P95 не публиковать как устойчивую оценку на такой маленькой выборке. Общий лимит latency пока не утверждён: сохранять `latencyTargetMs:null` и сравнивать фактические времена.
- Транспортные retries и повторные генерации из-за неверного ответа различать. Первые попытки не скрываются; «прошло с repair/retry» — отдельная метрика. Никакого бесконечного loop саморедактирования prompts.

## 8. Статусы и отчёт

Одна строка отчёта представляет точную конфигурацию. Поля:

| Конфигурация | Раунд / prompt hash | TC-001 строгие проверки | TC-002 строгие проверки | Семантическая оценка | Контроль переносимости | Время всех runs | Адаптация |
|---|---|---|---|---|---|---|---|
| … | baseline / adapted | pass count / repeats + первый diff | pass count / repeats + первый diff | pass/fail/uncertain/not reviewed | not run либо результат | cold, warm median/max, failures/retries | итерации, calls, минуты |

Сохранять раздельно `automaticVerdict`, `semanticVerdict`, `isolationVerdict`, `coverage` и `recommendation`. Возможны статусы `PASS`, `FAIL`, `REVIEW`, `NOT_RUN`, `ORACLE_CONFLICT`, `INFRA_ERROR`. Смесь успешных и неудачных repeats не считается PASS кейса. Если обязательная проверка не выполнялась, статус всей заявленной области — не PASS.

Рекомендация «кандидат на миграцию» требует прохождения заявленных автоматических проверок и смыслового review; скорость служит для сравнения прошедших кандидатов. Не вводить скрытый проходной балл, позволяющий обменять потерянное событие на выигрыш скорости. Живую миграцию/приёмку выполнять отдельно.

Run-папка: `work/model-eval/<batch>/<config>/<case>/<repeat>/`. В ней `run.json`, request/response каждого call, state before/after, trace, `automatic-diff.json`, пакет review, `judge-report.json`, итоговый report. Содержимое не перезаписывается следующей попыткой. Чувствительные входы хранятся локально.

## 9. Запуск матрицы и оставшийся scope

Исполнитель: [run_model_matrix.cjs](../../../tools/run_model_matrix.cjs). Конфигурация: [MATRIX.json](MATRIX.json). По умолчанию 18 независимых запусков: Gemma thinking, Qwen thinking и Qwen без thinking × TC-001/002 × 3. Все профили используют temperature=0, num_ctx=16384 и num_predict=8192. Это явный сравнительный профиль, не утверждение о текущих настройках пользовательского UI. Первичная диагностика на 8192 обнаружила Structured input=7492 и обрыв после 700 токенов thinking; её batch сохранён отдельно и не смешивается с новой конфигурацией. Серверные sampling defaults и native template сохраняются из `/api/show`; фактический request записывается для каждого call. Thinking/format/prompts автоматически не исправляются.

```text
npm run model-eval -- --dry-run
npm run model-eval
npm run model-eval -- --profiles qwen38-no-thinking --repeats 1
npm run model-eval:control
```

Без npm доступны те же параметры у `node tools/run_model_matrix.cjs`. `--config` выбирает отдельный файл конфигурации; `--cases TC-001,TC-002` и `--profiles` ограничивают матрицу. Один repeat — smoke, не qualification. Exit code 0 — весь заявленный автоматический scope прошёл; 1 — завершена матрица с расхождениями; 2 — ошибка подготовки/инфраструктуры или остановка. Наличие automatic PASS не означает semantic PASS или готовность к миграции.

[Oracle control](../../../tools/run_model_oracle_control.cjs) подаёт TC-001 заранее правильные ответы вместо сетевого backend и проверяет тот же core/Save path. Model/network calls = 0; результат не включается в статистику кандидатов. Если он расходится с oracle, это самостоятельное evidence проблемы интеграции либо сценария эталона, а не качества весов. Контроль сохраняет полный пакет и возвращает 1 при таком расхождении. Он не запускается автоматически обычным guard.

Первый завершённый batch: [результаты 18 runs](../../../work/model-eval/2026-09-26T23-23-25-159Z-2ab547/REPORT.md) и [разбор расхождений](../../../work/model-eval/2026-09-26T23-23-25-159Z-2ab547/ANALYSIS.md). В нём TC-001 Save расходится с двумя эталонными версиями даже на oracle control; автоматический FAIL сохраняется. Это не разрешение переписать oracle или считать модель готовой к миграции.

Перед запуском выполняется registry preflight. Изменение project source, evaluator, fixtures/oracles или personal main/tmp между runs останавливает batch. Модели должны быть уже установлены; downloads, правки production prompts и пользовательских данных не выполняются. GPU jobs идут по одной. Ошибочные ответы не перегенерируются evaluator; штатный consistency retry RuleUpdate остаётся частью core и виден как дополнительный call. Транспортные retries отключены.

Каждый core-run получает свою fixture, cache и main/tmp paths; обработка дней использует реальные предложения кандидата. После preview проверяется неизменность main. Затем в scratch вызывается проектный `commitRules` и сериализуются внешние `data={date,values}` и `graph={relations}`. Это проверка core и контрактов сериализации, **не браузерная Save-транзакция, reload или визуальная приёмка**.

Сравнение журналов заранее фиксирует projection: version, ровно одно правило в snapshot, точный mapping и упорядоченные examples. Runtime wrappers, IDs, raw описания и timestamps не представлены в canonical oracle и исключены из этого сравнения; полные файлы сохраняются для review. Данная проверка не подтверждает отсутствие всех лишних runtime полей. Cutter oracle — заранее сохранённые три ячейки каждого известного anchor; только HTML br/newline и внешние пробелы считаются эквивалентными. Это comparator fixture, не распознаватель пользовательских данных.

Таймаут одного call — 180 с, worker — 15 минут; данные/ответы сохраняются и при сбое. Снимки `/api/ps` и GPU до/после run показывают загрузку/контекст/offload; принудительное освобождение чужих процессов и принудительный cold reset не выполняются. Первый call со значимым `load_duration` отражён отдельно; warm-строки означают наблюдаемую загрузку каждого call < 1 с. Тихая внутренняя обрезка входа сервером не гарантированно обнаруживается: сохраняются input token count, num_ctx и сырые запросы; явный finish reason `length` даёт FAIL.

Артефакты находятся в `work/model-eval/<batch>/`. `REPORT.md` обновляется после каждого run, `summary.json` содержит счётчики строгого PASS, совпадения событий и Router отдельно. `review-packet.json` не содержит имени кандидата и timing metadata. Judge не запускается на GPU во время сравнительных измерений; рецензия выполняется отдельно по сохранённым пакетам. Batch хранит веса/digest/quant, native template, prompt hashes, эффективные запросы, environment и правила сравнения.

Также доступны специализированный [TC-002 runner](../../../tools/run_tc002_gemma_repeats.js), [Router probe](../../../work/model-research-2026-09-26/probe.cjs) и [общий шаблон отчёта](../EXECUTION_REPORT_TEMPLATE.md). Независимая квалификация каждой стадии на reference-derived контексте ими и новой core-матрицей не закрыта; текущие per-call контексты помечены observed.

Перед следующим экспериментом выполнить read-only preflight:

```text

```

Он проверяет зарегистрированные input/fixture/oracle/prompt hashes и целостность реестра. Он **не вызывает модель** и его зелёный результат **не означает**, что модель прошла кейсы.
