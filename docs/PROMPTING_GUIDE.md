# PROMPTING_GUIDE — промпт-инжиниринг для малых локальных LLM (Gemma 4 и подобных)

> Машиная документация. Назначение: устойчивая классификация (router/resolve) и повторное
> использование ключей (key reuse) на малых локальных моделях (наш случай: `gemma4` через Ollama).
> Всё, что здесь записано про наш движок, — факты из кода репозитория; всё остальное — с цитируемыми
> источниками [n]. Пользовательская документация (docs/user/) при конфликте имеет высший приоритет.

## 0. Наш стек (факты из кода)

- Модель: `gemma4` на локальной Ollama (`adapters/llm.js:20-21`).
- Транспорт: `/api/chat`, `stream:false`, ОДНО user-сообщение, **без system-роли и без
  temperature/seed/top_p в body** (`adapters/llm.js:67-71`) — см. §2.1, это главный найденный рычаг.
- 2 промпта сейчас (`prompts/mode_*.md`): `mode_router.md` (деление ввода на
  3 группы кусков по architecture.canvas), `mode_parse.md` (Branch 1: перевод в
  JSON-кандидаты). Плановые: `mode_minorRuleUpdate.md` (Branch 2),
  `mode_RuleUpdate.md` (Branch 3).
  Статус выводится из mode, не из модели (`adapters/llm.js` MODE_TO_STATUS).
- LLM — НЕ источник истины (AC10): детерминированный `responseParser` + интерпретатор валидируют
  и конвертируют кандидатов в события. Промптинг усиливает модель, но корректность гарантирует
  валидатор — это соответствует лучшей практике: «schema enforcement не гарантирует семантической
  корректности, пост-валидация обязательна» [5].
- Словарь смыслов `{{RULES}}` инжектится в промпт — это и есть механизм key reuse.

## 1. Универсальные практики для малых моделей

### 1.1 Температура и детерминизм

Классификация и извлечение — задачи с правильным ответом, не генерация. Одна и та же запись должна
давать один и тот же ключ при каждом прогоне: «the same input can produce different labels across
runs, especially at higher temperatures. For classification tasks, set temperature to 0» [3].
Для JSON-задач рекомендуют 0.0–0.1: «higher temperatures introduce the randomness that causes
format drift» [6]. Даже при temperature 0 остаётся вариативность (обновления модели, float-разница),
поэтому критичные пайплайны логируют вход и выход для аудита регрессий [3].

**Репо-рекомендация R1:** передавать в Ollama-body `temperature: 0` (доп. `top_k: 1` или
`top_p: 0.1` для отсечения хвоста) и `seed` из контекста прогона. Сейчас body этого не содержит
(`adapters/llm.js:67-71`) — Ollama по умолчанию использует temperature 0.8, т.е. наш движок
классифицирует при максимальной случайности. Дополнить `adapters/llm.js` (mode-независимые
sampling-поля) + тест в `tests/`.

### 1.2 Строгий JSON-контракт

Практики, сходящиеся во всех источниках:

- «Output ONLY the JSON object, nothing before or after»; запрет преамбул («Here is the JSON:»),
  markdown-заборов ``` и текста снаружи объекта [6].
- Схема в промпте явно: имена полей, типы, «case-sensitive — match exactly» [6].
- Отсутствующие данные — явно (`null`/пусто/дефолт), а не молчаливое пропуском поля: «Include all
  fields. Use null for any field not mentioned» [10]; ретрай с текстом
  конкретной ошибки валидации («expected string for field X, got null») успешен в ~70-80% схемных
  нарушений [5].
- Низкая температура — обязательное условие стабильного формата [3][6].

Наш контракт `{status, payload, confidence}` уже этому соответствует; `responseParser` — наш
«repair layer». Рекомендация R2 — не ослаблять: любые новые поля описывать с типом и правилом
решения («Set to true only if…»), а не общими словами [4].

### 1.3 Классификация: определения категорий + примеры на краевые случаи

Промпт «просто выбери категорию» ломается на ~30% записей; надёжная версия задаёт каждую категорию
ЯВНО, с примерами, и инструкция «примеры в определениях делают больше работы, чем сами
определения» [3]. Few-shot примеры должны показывать краевые случаи, а не только очевидные [3].
Обязателен выход «ни одна из категорий»: без него модель притянет ближайшую и «тихо испортит
данные» [3]. Few-shot остаётся эффективным вплоть до тысяч размеченных примеров:
«instruction-tuning of small language model with only 10 labelled samples… often leads to
performance on par, or better, than the one in much larger language models» — дообучение
стоит только при доказанном разрыве качества [7].

**Репо-соответствие:** router (mode_router.md) это уже делает — явные категории,
примеры, выход-иначе. Структуру «категории явно + примеры краевых случаев +
обязательный выход-иначе» сохранять при любых правках промптов (в т.ч. новых
minorRuleUpdate/ruleUpdate).

### 1.4 Key reuse (главная боль проекта)

Это частный случай консистентности ярлыков: модель должна возвращать управляемый словарь
(controlled vocabulary), а не свободные метки — «classification prompts fail when the model returns
verbose labels instead of controlled vocabulary» [3]. Стабильные практики:

1. **Инжектить актуальный словарь в промпт** и требовать точного совпадения: «используй ИМЕННО
   его, до буквы» (наш mode_parse.md D11). Это стандарт: enums «significantly reduce the effective
   vocabulary… which improves accuracy on smaller models» [5].
2. **Явное правило создания нового ключа** — аналог категории OTHER: «Новый ключ создавай ТОЛЬКО
   если подходящего в словаре НЕТ» (D11). Без явного выхода модель «форсит ближайшее совпадение» [3].
3. **Запрет на выдумывание полей-призраков:** «НЕ создавай _max-метрику», если в тексте нет
   максимума (D16) — это «optional field hallucination», известный режим отказа [5].
4. **Semantics over surface form:** сличать по смыслу правила (semantics/examples), а не по
   буквальному шаблону строки (наш router, п.3 порядка решения). Регекс/фильтр по форме —
   запрещён проектно (см. ПАМЯТКУ в AGENTS.md): «недетерминированный вход — ядро продукта».
5. **Примеры — с ПОЛНЫМИ значениями, один пример на вход** (коммит 63e2cd2). Фрагментарные
   представления одного входа N раз хуже: модель сличает по самой репрезентативной паре
   input→values, частичный вид ломает сличение.

### 1.5 Gemma-специфика

- Формат Instruct — `<start_of_turn>user … <end_of_turn><start_of_turn>model`; системной роли нет,
  инструкции вставляются в начало user-хода [1][8]. В Ollama `/api/chat` рендер шаблона делает сервер —
  нам достаточно корректного `messages`, но НЕ смешивать system-контент в ролях, которых шаблон
  gemma не знает (наш вариант — всё в user — безопасен).
- Gemma «may struggle with function calling due to a lack of training in that area»; zero-shot
  аgent-задачи ненадёжны, one/few-shot демонстрации в промпте заметно стабилизируют [2]. Отсюда:
  сложные ветвления (router) держим на few-shot примерах из `{{RULES}}`, а не на рассуждении
  «из головы».
- «Lock down the output format to reduce format drift» — прямой совет для продакшн-использования
  Gemma: JSON-схема + малая оценка регрессии при смене версий модели [9].

### 1.6 Отказ от догадок и калибровка

- «If you cannot extract a required field with high confidence, use the designated default value…
  rather than guessing» [6]; наш `ambiguous`-режим (OBSERVER, «НЕ угадывай») — та же идея [3].
- Confidence LLM — не калиброванная вероятность, но полезен относительный сигнал; порог
  confidence → human review даёт практичную гибридную систему [3]. У нас это уже Field 2 staging:
  низкий confidence = пользователь смотрит кандидат до persist (INV-2).

### 1.7 Ретраи с обратной связью

Просто повторить тот же промпт — бесполезно. Эффективен ретрай с текстом конкретной ошибки
валидации и исходным ответом [5][6]; потолок ретраев 2–3, после — эскалация человеку, а не
тихий частичный результат [5]. У нас resolve/OBSERVER-конвейер выполняет роль «второго прохода» —
сохранять принцип: ретрай несёт конкретную причину отказа, не «попробуй ещё раз».

## 2. Анти-паттерны (фиксируем как запреты для промптов и валидатора)

1. **Детерминированный фильтр поверх недетерминированного входа** (регекс формата
   `отжимания (A+B)`, порядок слов, фиксированный список групп). Проектно запрещено (AGENTS.md
   ПАМЯТКА); из литературы: распознаватель — модель, детерминизм — только верификатор [3][5].
2. **Безликие метрики** `way1/type2` — ломают и график, и обратную совместимость правил (D16 уже
   запрещает).
3. **Примеры-шаблоны как белый список групп** — модель начинает копировать примеры вместо чтения
   семантики записи (mode_parse.md, «Запреты», п.4).
4. **Смешение ролей:** промпт не источник истины; результат любого режима
   возвращается на детерминированную валидацию — соответствует AC10.
5. **Правки промпта молча:** промпт-изменения показывать пользователю на апрув ДО вшивания
   (нарушение = откат, память 2026-08-31). Версия промпта монотонна (`<!-- version: N -->`), INV-5.

## 3. Чек-лист правки промпта (минимальный гейт)

1. Правка сохраняет недетерминированный вход (никаких форматов-фильтров).
2. Правка не превращает примеры в белый список.
3. JSON-контракт: только JSON, схема с типами, явные дефолты/ambiguous-выход.
4. Few-shot примеры покрывают краевые случаи, один пример на вход, полные values.
5. `npm run guard` + `npm test` зелёные; `npm run build` после правок core/adapters/prompts.
6. Правка показана пользователю на апрув до вшивания; версия промпта увеличена.
